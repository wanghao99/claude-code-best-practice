## 逐字稿

### 开场介绍

我们非常兴奋迎来第一位特别嘉宾。他参与构建了现代 AI，然后向大众解释现代 AI，偶尔还给现代 AI 重新命名。他就在这间办公室里参与联合创立了 OpenAI；当年正是他让特斯拉的 Autopilot 真正跑了起来；他还有一种罕见的天赋，能让最复杂的技术变革显得既平易近人又理所当然。大家都知道他去年创造了 vibe coding 这个词，但就在最近几个月，他说了一句更让人吃惊的话：作为一个程序员，他从未感到如此落后。今天我们就从这里开始。谢谢你，Andrej。

你好。很高兴来到这里，我们开始吧。

### "从未感到如此落后"

就在几个月前，你说作为程序员你从未感到如此落后。这话从你嘴里说出来尤其令人吃惊。能展开讲讲吗？这种感觉是令人兴奋还是令人不安？

肯定两者都有。首先，和你们很多人一样，我用 Claude Code 这类 agentic 工具已经有一阵子了，大概从它去年发布开始。它很擅长写代码片段，偶尔会搞砸需要你手动修，总体挺有用。然后我要说 12 月是一个明显的转折点——我当时在休假，时间多一点，我想很多人也类似——我开始注意到，用最新的模型，代码片段直接就是对的，我不断提出更多要求，它还是直接就是对的，我已经想不起上一次纠正它是什么时候了。然后我就越来越信任这个系统，然后我就在 vibe coding 了。

这是一个非常陡峭的转变。我特意在 Twitter（现在是 X）上强调过这一点，因为很多人去年体验到的 AI 还是"ChatGPT 那样的东西"。但你真的需要重新审视，而且要以 12 月为节点审视，因为事情发生了根本性的变化——尤其是这种 agentic 的连贯工作流真的开始能用了。正是这个认识让我一头扎进了无穷无尽的业余项目。我的 side projects 文件夹塞满了各种随机的东西，一直在 vibe coding。我会说这大概就发生在 12 月，之后我一直在消化它的影响。

### Software 3.0：新的计算范式

你多次谈到 LLM 是一种新计算机的观点——它不是更好的软件，而是一个全新的计算范式。Software 1.0 是显式规则，Software 2.0 是学习出来的权重，Software 3.0 就是现在这个。如果这真的是对的，那么一个团队在真正相信这件事的那天起，会做出什么不一样的构建？

好。Software 1.0 是我写代码；Software 2.0 是我通过创建数据集和训练神经网络来"编程"，编程变成了组织数据集、目标函数和神经网络架构。接下来发生的事情是，如果你在一个足够大的任务集合上训练 GPT 这类模型或 LLM——由于在互联网上训练隐含地要求模型同时处理数据集中的所有任务——从某种意义上说，它们就变成了一台可编程的计算机。

所以 Software 3.0 是指你的编程变成了 prompting（提示），上下文窗口里的内容就是你操控那台解释器的杠杆——LLM 就是解释器，它解释你的上下文，在数字信息空间里执行计算。

有几个例子让我真正理解了这一点。比如 OpenClaw 发布时，你要安装 OpenClaw，按照惯例你会预期这是个 bash 脚本、shell 脚本，运行脚本来安装。但问题是，为了覆盖大量不同的平台和不同类型的电脑，这些 shell 脚本通常会膨胀得极其复杂——而你还是困在"要写代码"的 Software 1.0 世界里。而实际上 OpenClaw 的安装方式是复制粘贴一段文本，交给你的 agent。本质上它是一个小 skill："复制粘贴这段文字给你的 agent，它就会装好 OpenClaw。"这强大得多的原因是，你现在工作在 Software 3.0 范式里，不需要精确写出安装的每一个细节。agent 自带智能，它读指令、看你的环境和电脑、执行智能操作把事情跑通、在循环里自己调试。这强大太多了。所以这是一种非常不同的思维方式——要复制粘贴给 agent 的那段文本是什么？这就是编程范式。

### MenuGen 和"不该存在的应用"

还有一个更极端的例子，是我做 MenuGen 的时候。MenuGen 的想法是：你到一家餐厅，拿到菜单，通常没有图片，很多东西我都不知道是什么——大概 30% 的东西我不知道，有时 50%。所以我想拍一张餐厅菜单的照片，得到这些菜大概长什么样的一般化图片。

我 vibe coding 出了这个应用：上传照片，它做各种处理，跑在 Vercel 上，重新渲染菜单，列出所有条目，用图像生成器对每个标题生成图片展示给你。

然后我看到了这件事的 Software 3.0 版本——直接刷新我的认知——就是拍下照片，交给 Gemini，说"用 Nanobanana 把这些菜叠加到菜单上"。Nanobanana 返回的图片就是我拍的那张菜单，但它直接在像素里把菜单上不同的菜渲染了出来。这让我震惊，因为我整个 MenuGen 都是多余的，它在旧范式里工作。那个应用根本不该存在。

Software 3.0 范式更"生"。神经网络做了越来越多的工作，你的提示或上下文就是那张图片，输出也是一张图片，中间不需要任何应用。所以人们必须重新框定问题——不是在既有范式里把存在的东西加速，而是现在有全新的东西可用了。

回到你关于编程的问题——我认为那也是旧思维的例子，因为这不仅是编程变快。这是更一般的信息处理被自动化了，甚至不只关乎代码。以前的代码处理结构化数据，对吧？你针对结构化数据写代码。但比如我的 LLM 知识库项目——让 LLM 为你的组织或你个人创建 wiki——这甚至不是一个程序。它以前不可能存在，因为没有任何代码能基于一堆事实创建知识库。但现在你可以把这些文档拿出来，用不同的方式重新"编译"它们、重新组织它们，创造出新的、有趣的东西，作为数据的重新呈现。这些是以前不可能的新事物。所以我一直强调的不仅是"以前能做的事现在更快了"，而是出现了以前不可能的新机会——我几乎觉得这更令人兴奋。

### 外推到 2026 及以后

我喜欢你给出的 MenuGen 的递进和对照。如果进一步外推：90 年代建网站、2010 年代做移动应用、上一个云时代做 SaaS，那么今天的对应物是什么？哪些今天还基本没人做的东西，回头看时会显得理所当然？

继续用菜单的例子，很多这样的代码不该存在，就是神经网络做大部分工作。我认为外推的结果会非常奇怪，因为你可以想象某种意义上的完全神经网络计算机。你输入原始视频——想象一个设备把原始视频或音频直接喂给神经网络——然后用 diffusion 渲染出一个只属于那一刻的 UI。

我有点感觉，在计算的早期，人们其实有点困惑：计算机会长得像计算器，还是像神经网络。在五六十年代，走哪条路并不明显。我们当然走了计算器的路，建成了经典计算，而神经网络目前是虚拟化地跑在既有计算机上。但我认为这会发生翻转：神经网络变成宿主进程，CPU 变成协处理器。我们已经看到智能算力的图表——神经网络将接管并成为 FLOPs 支出的主体。所以你可以想象一个奇怪又陌生的未来：神经网络承担大部分重活，把工具调用当作某种历史附属品来处理少数确定性任务，但真正主导一切的是神经网络。外推的图景会非常陌生，但我认为我们会一步一步走到那里。

### 可验证性与锯齿状智能

我想谈谈可验证性这个概念——AI 会更快、更容易地自动化那些输出可以被验证的领域。如果这个框架是对的，什么工作即将比人们意识到的快得多地被改变？哪些被大家认为安全、实际上高度可验证的职业会受影响？

我花了一些时间写可验证性。传统计算机能轻松自动化你能用代码精确描述的东西，而这一轮 LLM 能轻松自动化你能验证的东西——因为前沿实验室训练这些 LLM 时，本质上是巨型强化学习环境。它们被给予可验证的奖励，由于训练方式，它们最终变成了这些锯齿状的实体：在可验证领域——数学、代码及邻近领域——能力达到峰值；在这个空间之外则停滞、毛糙。

我写可验证性的原因，是想理解为什么这些东西如此锯齿状。一部分与实验室怎么训模型有关，但一部分也与实验室的注意力焦点、恰好放进数据分布里的东西有关。有些东西在经济上明显更有价值，于是产生了更多的环境，因为实验室想在那些场景里发力。代码就是个好例子。可能有很多可验证的环境没能进入训练组合，仅仅因为具备那种能力没那么有用。

一个大谜题——之前大家最爱举的例子是"strawberry 里有几个 r"，模型 famously 会答错，这是锯齿状的一个例子。现在模型已经补上了。新的例子是："我要去洗车，洗车点在 50 米外，我该开车还是走路？"当前最先进的模型会告诉你走路，因为很近。怎么可能最先进的 Opus 4.7 一边能重构十万行代码库、找零日漏洞，一边却让我走路去洗车？这太离谱了。

只要这些模型还是锯齿状的，就说明：第一，可能有些东西还不对；第二，你需要保持在环里一点，把它们当工具对待，确实需要保持对它们在做什么的感知。长话短说，我关于可验证性的全部写作，就是在试图理解为什么这些东西是锯齿状的。有规律吗？我认为是"可验证 + 实验室在乎"的某种组合。

也许再举一个有启发性的轶事：从 GPT-3.5 到 GPT-4，人们注意到国际象棋进步很大，很多人以为"这只是能力的自然提升"——但实际上主要是大量棋类数据进入了预训练集，仅仅因为在数据分布里，模型的提升就远超默认水平。OpenAI 的某个人决定加入这些数据，于是这个能力就突飞猛进。

这就是我强调这个维度的原因：我们在某种程度上受制于实验室在做什么、他们恰好往组合里放了什么。你必须自己去探索这个没有说明书的东西。它在某些场景下好用，另一些场景不行。如果你处在 RL 覆盖的回路里，你飞起来；如果你处在数据分布之外的回路里，你会很挣扎——你必须搞清楚你的应用处在哪个回路里。如果不在回路里，那你就得认真考虑微调和自己做些工作，因为它不会开箱即用地从 LLM 里冒出来。

### 给创始人的建议

如果你今天是一位创始人，想创建公司，解决一个你认为可解的问题——一个可验证的领域——但你环顾四周发现："天哪，实验室在最显眼的领域——数学、编码等——真的开始进入逃逸速度了。"你会对在座的创始人提什么建议？

我确实认为可验证性让一件事在当前范式下可解，因为你可以往上面砸海量 RL。一种看法是：即使实验室没有直接聚焦，这一点依然成立。所以如果你处在可验证的场景里，能够创建这些 RL 环境或样本，这实际上让你有机会做自己的微调，你可能从中受益。这本质上是一种"就是有效"的技术。如果你有海量多样的 RL 环境数据集，你可以拉下杠杆——用你喜欢的微调框架，得到一个确实效果不错的东西。

我确实认为存在一些非常有价值的强化学习环境，是人们可以想到但实验室没在做的。我不想把答案说出来，但确实有一个我认为非常有价值的领域。抱歉，我不是想在台上"发模糊帖"，但这样的例子是存在的。

反过来，你觉得什么东西只有远远看去才显得可自动化？

我确实认为最终几乎所有东西都能在某种程度上变得可验证——有些容易有些难。因为即使是写作这类事情，你也可以想象有一个 LLM 评委委员会，通过这种方式得到合理的结果。所以更多是难易之分。我认为最终一切皆可自动化。

### Vibe Coding 与 Agentic Engineering

去年你创造了 vibe coding 这个词，而今天我们处在一个感觉更严肃一点的世界——agentic engineering。你认为两者的区别是什么？你会怎么称呼我们今天所处的阶段？

好。我会说，vibe coding 是抬高所有人做软件的地板。地板抬高了，人人都能 vibe code 任何东西，这很棒、不可思议。而 agentic engineering 是在专业软件中保住之前就存在的质量标准。你不能因为 vibe coding 引入漏洞。你对你的软件仍然像以前一样负责，但你能更快吗？剧透：能。那怎么正确地做到？所以对我来说，agentic engineering——我这么叫它，因为我确实认为它是一门工程学科——就是：你有这些尖刺状的 agent 实体，它们有点易错、有点随机，但极其强大。你如何协调它们跑得更快而不牺牲质量标准？把这做好、做对，就是 agentic engineering 的领域。

所以我视两者为不同——一个抬高地板，一个向上外推。而且我看到 agentic 工程师的能力上限非常高。以前人们谈 10x 工程师——我认为这个倍数被放大了很多。10x 已经不是你能获得的加速了。在我看来，非常擅长此事的人，峰值远超 10x。

### AI 原生编码长什么样

Sam Altman 去年来 AI Engineer 时说过一句令人印象深刻的话：不同世代的人用 ChatGPT 的方式不同。如果你三十多岁，你把它当 Google 搜索的替代品；但如果你十几岁，ChatGPT 就是你接入互联网的入口。今天在编码领域对应的平行现象是什么？如果我们观察两个人用 OpenClaw、Claude Code、Codex 编程——一个你认为是平庸的，一个你认为完全 AI 原生——你会怎么描述区别？

我认为就是把可用工具的性能榨到极致——利用它们的所有功能，投入建设自己的配置。就像以前所有工程师都会把工具用到极致——无论是 Vim、VS Code，还是现在的 Claude Code 或 Codex——投入建设你的 setup，利用大量可用的工具。我觉得大概就是这个样子。

一个相关的想法——很多人现在可能在为此招聘，因为他们想招强大的 agentic 工程师。但我认为大多数人还没有为考察 agentic 工程能力重构他们的招聘流程。如果你还在发算法题让人解，这还是旧范式。我会说招聘应该长这样：给一个真正大的项目，看这个人实现这个大项目。比如"让我们给 agent 写一个 Twitter 克隆"，把它做得很好、很安全，然后让一些 agent 在这个 Twitter 上模拟活动，然后我用 10 个 Codex 5.4 xhigh 试图攻破你部署的网站——它们试图攻破，但应该攻不破。也许招聘长这样。在那个场景下观察人，构建更大的项目、利用工具链，大体就是我会看的东西。

### 品味、判断与环中之人

当 agent 做得越来越多，什么人类技能变得更值钱而不是更不值钱？

现在的答案是：agent 有点像实习生。所以值得注意的是，你仍然要负责审美、判断、品味，以及一点点监督。

我最喜欢的 agent 之怪异的例子之一是：MenuGen 用 Google 账号注册，但用 Stripe 账号购买点数，两者都有邮箱地址。我的 agent 在购买点数时，居然试图用 Stripe 的邮箱去匹配 Google 的邮箱——就好像不存在一个持久的用户 ID 一样。它想靠邮箱地址把人对上，但你的 Stripe 和 Google 可以用不同邮箱，资金就对不上号了。这就是 agent 仍会犯的错误——为什么你要用邮箱地址来关联资金？邮箱可以是任意的，可以用不同的邮箱，这么做太奇怪了。

所以我认为人必须负责 spec（规格）、负责 plan。其实我甚至不太喜欢 plan mode。它显然很有用，但我觉得更一般的东西是：你必须和你的 agent 一起设计一个非常详细的 spec——也许基本上就是文档——然后让 agent 去写，你负责监督和顶层分类，agent 做大量台面下的工作，你不用关心某些细节。

再举一个数组或张量的例子。PyTorch、NumPy、Pandas 等等各种小 API 细节多得要命。我已经不记得 keep_dims 还是 keep_dim，参数是 `dim` 还是 `axis`，是 reshape、permute 还是 transpose 了。这些我都不记了，因为不需要记。这类细节交给"实习生"处理，因为它们记性极好。但你仍然必须知道：底层有一个 tensor、有一个 view，你可以操作同一存储的 view，也可以用不同的存储（那会更低效）。你仍然要理解这些东西在干什么、理解一些 fundamentals，这样才不会无谓地来回拷贝内存。但 API 的细节已经交出去了。你负责品味、工程、设计——负责"这事讲得通"以及"你要的是对的东西"。比如：这些必须是唯一的用户 ID，一切都要挂到它上面。你做一部分设计与开发，"工程师们"做填空题。这就是我们目前所处的位置。

你觉得这种品味和判断会随时间变得不重要吗，还是上限会一直抬高？

我希望能改进。现在它不改进的原因，可能还是那句话：它不在 RL 里。大概没有审美的代价或奖励，或者还不够好。我看那些代码时，有时候真的有点心脏病发作——因为它不一定总是特别惊艳的代码，很臃肿、大量复制粘贴、有别扭而脆弱的抽象，能跑但真的很恶心。我确实希望未来的模型能改进。

还有一个好例子是 microGPT 项目，我试图把 LLM 训练简化到极致。模型讨厌这个，做不来。我不断提示 LLM 再简化、再简化，它就是做不到。你会感觉自己处在 RL 回路之外，像拔牙一样，完全不是光速。所以我确实认为人仍然要负责这部分。但没有什么根本性的东西阻止它变好——几乎只是实验室还没做而已。

### 动物与幽灵：理解 LLM 是什么

我想回到锯齿状智能这个话题。你写过一篇发人深省的文章，关于动物与幽灵。观点是：我们不是在造动物，我们是在召唤幽灵。这些是锯齿状的智能，由数据和奖励函数塑造，而不是由内在动机、乐趣、好奇心或掌控欲塑造——那些是演化赋予的。为什么这个框架重要？它实际改变了你构建、部署、评估甚至信任它们的方式吗？

我写这个的原因是我想搞明白这些东西到底是什么。因为如果你对它们是什么、不是什么有一个好的模型，你使用它们就会更称职。我不确定它是否真的有实际效力，有点像哲学思辨。但它就是让你接受一个事实：这些东西不是动物智能。你对它们大吼大叫，它们不会做得更好或更差——毫无影响。它全部只是统计模拟回路，基底是预训练（也就是统计），上面螺栓固定着 RL，于是"附肢"变多了。也许它只是一种心态：你带着什么预期进场，什么更可能有效或无效，怎么修改它。但我并没有"让你的系统变好的五个显然结论"，更多只是对它保持怀疑、随时间摸索。这就是起点。

### Agent 原生基础设施

你在深度使用那些不只是聊天的 agent——它们有真实权限、有本地上下文、真的替你执行操作。当我们所有人都开始生活在那个世界里时，世界会是什么样？

我想在座的很多人都在期待 agent 原生环境的样子。一切都必须重写。一切从根本上还是为人写的，必须被挪动。我现在用各种框架、库之类的东西时，它们的文档从根本上还是为人写的。这是我最爱的吐槽点。为什么大家还在告诉我"该怎么做"？我什么都不想做。我应该复制粘贴给我的 agent 的那段东西在哪？每次别人告诉我"去这个 URL"之类的，我就——啊。

所有人都在兴奋地讨论：怎么把需要发生的工作负载分解成对世界的传感器和执行器，怎么让它 agent 原生——先讲给 agent 听，然后围绕对 LLM 非常易读的数据结构做大量自动化。

MenuGen 出名的一点是，我写那篇博文时的麻烦根本不在写代码，而在部署到 Vercel——我不得不跟一堆不同的服务打交道，把它们串起来，进它们的设置和菜单，配我的 DNS，烦死了。所以这是个好例子：我希望 MenuGen 可以是我给 LLM 一个 prompt"构建 MenuGen"，然后我什么都不用碰，它就以同样的方式部署到互联网上。我认为这会是检验我们的基础设施是否越来越 agent 原生的一个好测试。

最终我认为我们会走向一个世界里：人和组织都有 agent 代理。"让我的 agent 和你的 agent 谈"，来敲定会议细节之类的事情。我认为大方向就是这样。

### 教育：外包思考，不能外包理解

我们必须以一个关于教育的问题收尾。因为你大概是世界上最擅长把复杂技术概念讲简单的人之一，也对如何围绕它设计教育有深度思考。当智能变得廉价、我们进入 AI 的下一个时代，还有什么值得深入学习？

最近有一条推文刷新了我的认知，我隔天就会想起来。大意是：**"你可以外包你的思考，但你不能外包你的理解。"**

我觉得这说得太好了。因为我仍然是系统的一部分，信息仍然得以某种方式进入我的大脑，而我觉得自己正在变成一个瓶颈——光是知道我们要构建什么、为什么值得做、我怎么指挥我的 agent，就已经是瓶颈。所以我仍然认为，最终必须有东西来指挥思考和处理，而这从根本上仍然受制于理解。

这也是我对所有 LLM 知识库感到兴奋的一个原因——因为我觉得那是我处理信息的一种方式。每当我看到信息被投影成一个不同的切面，我都觉得获得了洞见。所以对我来说，这就是对固定数据做合成数据生成的大量 prompt。我每次读文章都很享受——我有那个由这些文章构建起来的 wiki，我喜欢就各种事情提问。我认为归根结底，这些是以某种方式增强理解的工具。理解仍然是瓶颈，因为你不理解就没法当好指挥——LLM 显然不擅长理解，你仍然独一无二地负责这件事。所以这方面的工具，我认为极其有趣、令人兴奋。

我很期待几年后回到这里，看看我们是否已被完全自动化出环，连理解也被它们包办了。非常感谢你的参与，Andrej。
