## 逐字稿

### 欢迎与准备

好，各位，满员了，我们开始吧。我不想让你们再干等 25 分钟等什么人为的截止时间。欢迎。我叫 Matt，是个老师，现在算是教 AI 的。这里有个链接，还没看过的可以上去拿今天要做的练习。这场大约两个小时，我们就此开场。对吧 Mike？好，完美。

这场工作坊背后的理论——或者说过去六个月我一直按它行事的主题——是：我们都认为 AI 是一个新范式，对吧？AI 显然在改变很多东西，你们显然对此感兴趣，不然不会来。而我觉得，当我们说"AI 是新范式"的时候，我们忘了：软件工程的基本功，那些与人协作至关重要的东西，跟 AI 协作也同样好用。这是我明天主题演讲的内容，会在那里面展开更多。在这个工作坊里，我希望能把你们的注意力引到这些事上，希望能向你们证明我是对的——走着瞧。

先快速举手调查：有多少人用 AI 写过代码？用 AI 写过代码的举手。很好，手别放，让大家欣赏一下你们的腋下。有多少人每天都在用 AI 写代码？好。用过 AI 并且被它气到过的，手继续举着。非常好，手可以放下了。感谢配合，我很感动。

我们同时在向 Gilgood 会议室直播。有没有派人去 Gilgood 看看他们还好吗？不知道，但我看到你们了。参与方式是问答环节。说实话我有点讨厌 Q&A，因为它不民主：通常是话最多的人得到提问机会。所以我们用这个在线问答：为什么非得等到 3:45？房间挤满了、门关了，百分百同意。想提问的，请涌进这个异步问答，我们互相投票，让最好的问题浮上来，让全场受益。

### LLM 的约束：聪明区 vs 笨区

我想先讲 LLM 的一些奇怪约束，我们的很多工作都要围绕这些约束来建。有个叫 Dex Horthy 的人，经营一家叫 HumanLayer 的公司，他提出了一个概念：跟 LLM 协作时有聪明区（smart zone）和笨区（dumb zone）。当你刚开始一段新对话、从零起步时，LLM 会拿出它最好的表现，因为在那情况下注意力关系的张力最小。

你往 LLM 里每加一个 token，就像往足球联赛里加一支球队：想想每加一支球队要增加多少场比赛——平方级增长。因为注意力关系本质上是从每个 token 指向其他 token 的，既带位置又带语义。这意味着大约到 40% 左右——我现在的新标尺是大约 100K——不管你用的是 100 万上下文窗口还是 200K，都差不多是这个点，它开始变笨。往同一个上下文窗口里不停加东西，它就越来越笨，直到做出愚蠢的决定。觉得这很熟悉的，举手。对吧。

这意味着我们要把任务的大小控制在聪明区里，别让 AI 咬下嚼不动的分量。这其实是老建议了：Martin Fowler 在《重构》里讲过，《程序员修炼之道》也讲过——别贪多嚼不烂。把任务切小，让你这个人类开发者不会慌、不会自己进入笨区。

### 多阶段计划与 Ralph Wiggum 循环

可大任务怎么办？像"克隆一家公司"或者什么疯狂的大活，怎么拆成小任务让它们都落在聪明区里？一种做法——大概是 AI 公司希望你做的、也是最自然的做法——就是一直跑一直跑：冲进笨区，每个请求烧掉海量 token，然后压缩（compact）回去——压缩我们一会儿好好讲——再继续跑、跑、跑，再压缩，再跑。我觉得这不太行，因为沉积物会越积越多，这个也一会儿讲。

所以当时的理论——我自己也用了一阵——是多阶段计划：好，我们有个"4 号"这种大任务，把它拆成小节，分块处理，每小块都在聪明区里完成。用过"多阶段计划"的举手。对，非常普遍的做法，我们一直这么干，我至少用到去年 12 月。

而任何合格的开发者看到这个都会说："这不就是循环吗？阶段一、二、三、四……为什么不直接叫阶段 n？"阶段 n 的意思是：我们有一个在后台运行的计划，然后在它上面循环，直到完成。听说过"Ralph Wiggum"这种软件实践的举手。好。没听说过的举手——这就对了。Ralph Wiggum 大致是基于这个想法：你只需要说清楚旅程的终点，比如写一份 PRD（产品需求文档）说明我们要去哪，然后对 AI 说：每次做一个小改动，让我们离终点越来越近。Ralph 是能用的，但我更喜欢多一点结构。这就是我们在"聪明区"话题上的思考进展。

### LLM 像《记忆碎片》里的男主角

LLM 的另一个奇怪约束：它像《记忆碎片》（Memento）里的男主，不停遗忘，随时会重置回基础状态。我拉一下这张图。我真该做幻灯片，但我就是喜欢在一张无限大的 TLDraw 画布上到处滚。谢谢你，Steve。

另一个我想让你们建立的概念：每一段与 LLM 的会话都经历相同的阶段。最前面是系统提示词，这个灰框里的东西永远在你的上下文里。你要让它尽可能小——要是塞了 25 万 token 进去（我见过有人这么干），那你什么都还没做就直接进了笨区。所以这块要极小。然后进入探索阶段，这个蓝色是 coding agent 出去探索代码库。然后是实现，然后是测试和验证、跑反馈循环。感觉眼熟的举手。对，任何会话的几大基石。

而当你清空上下文，你直接回到系统提示词，"砰"，回到原点，之前的一切全删掉。听说过 compacting（压缩）的举手。好，有人没听说过，快速演示一下这是什么。比如我刚和我的 LLM 聊了一小会——我想确保把这些基础都过一遍，大家在同一波长上。我刚才在跟 LLM 聊，讨论我想做的东西。字体大小怎么样？要不要调大？后排的朋友？调调调。

我这场用的是 Claude Code，但你不必用 Claude Code，事实上不用 Claude Code 有时反而更好。我刚才在跟 LLM 聊，规划接下来做什么，它问我一堆问题——我强烈推荐你们这么干。这里有个小小的状态栏，告诉我正在用多少 token，精确数字。我网站 AI Hero 上有篇文章，想抄的可以去抄。这——哇，屏幕晃了一下——是每个编码会话里的关键信息：你必须确切知道自己在用多少 token，才知道离笨区还有多近。绝对关键。

看好了，我有两个选择：clear（清空），回到一无所有；或者 compact（压缩）。压缩的话，它会把整段对话——虽然 admittedly 不多——挤进一个小得多的空间。画成图就是这样：你把会话里的所有信息整理成一份"历史"，一份发生过什么的书面记录。开发者不知为何热爱压缩，但我恨它。我更希望我的 AI 像《记忆碎片》男主那样行事，因为这个状态永远一样、永远一样。每次清空都回到开头。如果你能做到这一点、能为此优化，你就处于非常好的位置。

这就是关于 LLM 我要你们记住的两件事、两个约束：它们有聪明区和笨区；它们像《记忆碎片》男主。

### 练习 1：Grill Me skill

来看第一个练习。我演示的时候，希望你们也跟着动手敲。刚才是小讲课，现在真刀真枪写点东西。

迟到的人和 Gilgood 房间的朋友：去这个链接看练习、clone 仓库。不弄也完全可以，光看我做也行。我自己来，看看有什么练习等着我们。这是我课程里的项目：一个课程管理平台，算是给讲师管理学生的 CMS，我们要在里面做一个功能。我会带你从功能点子出发，一路走到为它写 PRD，再到实现它，希望你从这个过程里获得灵感，用到自己的工作里。

开始。我们要用一个我特别有感情的 skill：grill me。这个 skill 妙在小、极小。它防的是我认为与 AI 协作的最大问题之一：错位（misalignment）。

我在这反对的潜流叫"specs to code"运动。有人听说过吗？举手。其实算不上运动，就是一群人喊"specs to code"。意思是：你要写程序、做 App，最好的方式是先写规格——某种文档——然后把文档变成代码。怎么变？丢给 AI。如果产出的代码有问题，你不看代码，你回头看规格、改规格，如此往复。这其实就是 vibe coding 换了个名字：你无视代码、不用管代码，只管编辑规格，一直走下去。我试过，真试过，糟透了、行不通，因为你必须握住代码：你需要理解里面是什么、需要塑造它，因为代码才是你的战场。

### 用 Grill Me 拷问 Sarah Chen 的 Slack 简报

这就是我们要走的路。来做练习：去这个页面，grill me skill。仓库里有一条 Slack 消息，在仓库根目录，文件叫 clientbrief.md，是 Sarah Chen 发的。不知为何 Claude 总选 Sarah Chen 当名字，不知道为什么。消息说：在 Cadence（我们的课程平台）里，留存数据不乐观，学生注册、上几节课就流失了，我想给平台加点游戏化。面对这样一个点子，你得找到把它落地的办法。假设 Sarah Chen 是你的客户，预算紧、工期快，你怎么做？

会进 plan mode 的举手？plan mode 重度用户？好。快速喊几个别的想法：你的第一反应是什么？对，没错。设想 Sarah Chen 挂机了、不在，你对她一无所知，她只发了这条消息，你要在走之前把它消化掉。

我的第一套流程是上这个 skill。我会清空上下文，把刚才那些都清掉，然后调用 skill——grill me skill。快速确认：不知道我在干嘛的举手。好，说得更具体点：我打一个斜杠再输入东西，明白这是什么吗？我在调用一个 skill，grill me skill。我要说 grill me，把客户简报传进去。现在 LLM 手里只有两样东西：skill，和我要做的事的描述。

这几乎是我每次用 AI 开工的方式。它探索代码库的时候，我给你们看看 grill me skill 的内容，就在仓库里，极短："就这个计划的每一个方面无情地采访我，直到我们达成共同理解。沿着设计树的每个分支走下去，逐个解决依赖。每个问题都给出你推荐的答案。一次只问一个问题。"等等等等。

它的作用是什么？我注意到跟 AI 协作——尤其是在 plan mode 里——它会特别急切地想给我出计划："我觉得信息够了，我来出计划吧。"而我发现自己真正想找词形容的不是那个。Frederick P. Brooks 在《设计原本》（The Design of Design）里有句很好的话，讲设计概念：当你和别人一起造新东西时，所有参与者之间共享着一个想法，那就是设计概念。我意识到我跟 Claude 之间需要的正是这个：达成共同理解。我需要的不是一份资产、不是一份计划，我需要跟 AI、跟我的 agent 在同一波长上。而这是一个极其有效的手段。

好，它探索完了。漂亮。它先调用了一个 subagent，在 Opus 上烧了 93.7K token，然后问了我第一个问题。注意：虽然 subagent 烧了一大堆 token，我的 token 用量其实没涨多少。

不知道 subagent 是什么的举手？这问题重要。大家都清楚吗？好，我给个简短定义：这里这个 explore subagent，本质上是去调了另一个 LLM，那个 LLM 有独立的上下文窗口，干完活把摘要汇报回来。所以 subagent 大概就是一次委托：你把任务委托给 subagent，它兴致勃勃地全干完、探索一大堆，然后把重要的东西一点点喂回给编排它的父 agent。

好，它做完了 explore，第一个问题来了：积分经济。哪些行为赚积分、各多少分？顺便说，这时你也可以反过来问它问题，加深你对仓库的理解。我显然对这个仓库很熟，因为是我写的，但你们可能不知道里面什么情况。比如它推荐"保持简单，两种积分来源起步"。这个模式妙就妙在：不仅问题让我们对齐，还附赠推荐。而且我常发现 AI 的推荐真不错。我就说：跳过视频、观看事件——它们噪声大、可刷分。同意。Sarah 问的"保留课程为基本盘"？嗯，不错，老伙计。

我平时是对 AI 口述的——真的是语音对话而不是打字——但这台笔记本比较新，听写软件装不上，因为 Windows 很糟。下一个问题：积分要不要回溯？已有课程进度记录，我们在补全时间戳。这是个特别刁的问题：要不要回头把所有课程进度事件都补录进去？要把功能做对，这类问题必须先对齐。这个我从没想过，Sarah Chen 肯定也没想过。要不要回溯？嗯，现场投个票吧：觉得应该回补所有记录的举手；觉得不应该的举手。骑墙的不少。我要说的是：这就是你跟 AI 进行的那种讨论，你们在一步步对齐。算了，我就采纳它的推荐，因为我懒。

注意我在这整个过程中是怎么保持"在环"的：它很快地向我抛问题，我不需要跑去刷 Twitter。等级：成长曲线是什么样？嗯，看着合理，就这个。好。你应该能这样跟 AI 一路走下来，达成对齐。这个 grill me 会话可以很长：它问过我 40 个问题，问过我 80 个，有人被问过 100 个——你就坐在那跟 AI 聊一小时。最后你得到的是这段对话历史，它本身就是一份极好的资产，是你正在创造的设计概念的资产。

它还能这么用：你去和某个领域专家开会，比如我和 Sarah 开个会，把会议逐字稿喂给 Gemini Meetings 或者你们用的任何工具，再把产出喂进一场 grilling 会话，把你们当初没有的假设拷问一遍。所以这是把外部输入接进来并做验证的极佳方式。

### 问答：框架、结对编程、人在环

好。我真想走到头，但也不想当着你们的面跟 AI 大眼瞪小眼一千天，所以我就直接说"是"。趁你们本地自己玩的时候，我们开个小 Q&A。

连击（streak）算积分吗？连击独立计算。看它还能出什么。游戏化 UI 放哪？放 dashboard 里。我就扫一眼快速过。Slido 进展如何？

"试过 Spec Kit、OpenSpec、Taskmaster 代替 grill me skill 吗？它们更啰嗦还是更结构化？"好问题。市面上有一大堆框架帮你搭这套规划流程。我个人认为，在这个没有明确赢家、没有唯一正道、一切都在变的阶段，你应该尽可能多地拥有你自己的规划栈。我和我很多学生观察到的问题是：他们过度使用某个栈，出了问题，因为栈不是自己的、对整体没有可观测性，就只会说"这不行，垃圾"。而如果你对整条链路有掌控，至少你知道怎么修、或者有可能知道怎么修。所以尽管我在给你们推荐一套栈，我信的是控制反转——栈应该归你掌控。

"grill me 问的很多问题未必适合开发者，更适合大团队里的 PO，谁该用它？"嗯。做过结对编程（pair programming）的举手？跟 AI 做过结对编程的再举一次？怎么样，好吗？爽吗？我觉得和 AI 的结对编程是个好主意，因为屋里多了个会无情考你的第三者。如果你不知道答案，应该是你 + 领域专家 + AI 同处一室；如果是实现问题，应该是你 + 另一位开发者 + AI 同处一室。你们可以在团队里这样过问题。一会儿我们讲实现时会看到怎么把实现做得飞快。但真正关键的那些决策——需要人类的那部分——其实需要很多人类，人多人少无所谓，完全可以来一群，基本就是"AI 版 mob programming"。

"我最爱的元提示（metaprompting）工具？"刚才答过了。没空调，忍着。"grill 会话之后怎么把对话当资产用？"后面会讲到。

好，我想人为加速一下。有人刚才说"那直接 Ralph 循环跑它啊"。但这里有个关键：这个我没法循环。我把 AI 时代的任务分两类：**人在环任务（human in the loop）**——必须有人坐在那做，比如现在这场，我们就是环里的那个人，还是多人在环；还有 **AFK 任务**——人可以离开键盘（away from keyboard），走开也没事。实现，我们后面会看到，可以变成 AFK 任务；但规划、这个对齐阶段，必须是人在环。必须。所以只能我来，没办法。

"把你所有的推荐列个长单子给我。我在开工作坊，所以需要你多分担点。"看它怎么办。趁它干活，再答两个问题。

"怎么看 PM 或其他非开发角色 vibe coding？"稍后专门讲，先留个悬念。

"为什么 grill me 不用 ask user question 那个提问 UI？"Claude Code 里有个专门的 UI——用 ask user question 工具向我提问——我快速答一下：这个 UI 在 Claude 里就是坏的，我很讨厌它。你们看到我在用 Claude，但我其实不太喜欢 Claude。用我这套方法，你真的可以随便选任何顺手的系统。这个 UI 长这样，第一次见挺讨喜，然后你就会发现它坏得一塌糊涂。

### 两份文档：目的地与旅程

好，它返回了什么？哦天。趁它干活，我先讲点东西。这里的计划是：拿着 grill me 的产出，找到某种方式把它变成一个"目的地"。我们在干嘛？我们在摸清形状——在 grilling 会话里摸清任务的形状。要把它变成 AI 可执行的一串动作，我们本质上要确定目的地：知道要去哪、知道整件事的形状。

所以我认为需要两份核心文档：一份记录目的地，一份记录旅程。换句话说，一份要弄清这东西到底长什么样——全部用户故事、完成的定义（definition of done）；另一份要弄清怎么切分。

这就是下一站。grilling 会话一结束——嗯，看着不错，太棒了，爱了。它自己答了自己的 22 个问题。这就是一场 grilling 会话的代表性样子。此时我用了 2.5 万 token，而这里面全是金子，我想留着：我手里有 25K 好token。我要做的就是把它总结进某种"目的地文档"。

### 练习 2：写 PRD

### 练习 3：PRD 转 issues——垂直切片与曳光弹

好，我们有了 PRD——我不打算读的那种目的地文档。快速扫一眼有没有好问题再往前冲。"重新发现软件工程师在当今世界的角色。推荐前三门学科。"呃，跆拳道不错。我完全不知道怎么答这个问题，不过谢谢提问。前三学科……管道工吧，管道工挺好。嗯，不知道这算不算学科，我雇过的管道工通常都不太自律。

好，我们有目的地了。完美。那怎么真正走到目的地？我们有一份模糊的 PRD，怎么切它才不会掉进笨区？换句话说，我们有那个"4 号"，怎么拆成这种多阶段计划？这个节点上你大概会说："Claude，给我一个通往这个目的地的多阶段计划。"合理，我们以前就这么干。但我现在有更好的做法：把它做成一块看板（Kanban board）。

不知道看板是什么的举手。好。看板本质就是一组贴在墙上的工单，彼此之间有阻塞关系。看这里的展示。这是我们开发者自敏捷以来的长期工作方式。看它给的：它提议把工作切成五个任务。第一个：schema 和 gamification service。看着不错，不被任何任务阻塞。还能看到它标了类型 AFK——记得我前面讲的人在环和 AFK 吧，这就是个 AFK 任务，可以直接甩给 agent 干。连击跟踪（streak tracking），不错。然后把积分和连击接进课程/测验完成——被 1 和 2 阻塞。回溯回填（retroactive backfill）——只被 1 阻塞。最后这个被上面全部阻塞。好。

这时你可能会问：为什么不把"生成 issues"这步也交给 AI？我为什么要在场？它给的东西已经挺像样了，我为什么还要评审、还要想下一步？我的看法：有了 PRD 之后这步非常便宜、非常快，而且我立刻能看出问题。这里有一个在决定"旅程形状"时极其重要的技巧，来自《程序员修炼之道》的非常经典的概念：**曳光弹（tracer bullets）**或**垂直切片（vertical slices）**。

曳光弹真的改变了我让 AI 自己挑任务的方式。系统是分层的：可能是不同的部署单元——数据库在一处，API 在数据库附近但独立部署，前端在完全不同的地方比如 CDN；部署单元内部还可能再分层。比如我们正在用的这个代码库里有一大堆 service：quiz service、team service、user service、coupon service、course service，它们互相有依赖，各自就是一层。

而我注意到，AI 特别爱横着写代码，一层一层来：第一阶段做完所有数据库的事、所有 schema、跟那个部署单元相关的所有东西；第二阶段做完所有 API；第三阶段把前端叠上去。谁能说说这画面错在哪？为什么不合适？有答案的举手。（观众："整个反馈循环要到最后才有。"）完全正确。你要到第三阶段才对工作获得反馈——不到第三阶段，你根本没有在测"所有层能不能协同工作"，手里没有一个可以测的集成系统。

所以你要想的是纵向的层：薄薄的、按需贯穿所有层的功能切片。这是更好的工作方式，对 AI 更是——因为第一阶段结束时（甚至进行中），它就能对整条流获得反馈。

这意味着什么？在我这个 PRD-to-issues 的 skill 里写的是："用垂直切片把 PRD 拆成可独立认领的 issues，以本地 markdown 文件落盘。"我们先定位 PRD，是新会话就再探索一遍代码库，然后起草垂直切片——把 PRD 拆成曳光弹式 issues。顺便说"曳光弹"这个名字：你是防空炮手——这画面其实挺暴力的——夜里对着天打，普通子弹你根本看不到弹道：看得见飞机、看不见自己的子弹去哪了。曳光弹是给每若干发子弹之一掺一点磷光物质，让它飞行时发光，于是天上出现一条线，你对瞄准有了反馈。这里的意思就是：提高反馈密度，对我们在造的东西获得近乎即时的反馈——否则 AI 在后期阶段之前等于盲写。

还有一组垂直切片规则：询问用户，然后创建 issue 文件。看它现在给的：尽管我说了要垂直切片，它还是提议先单独建 gamification service——那就只是一个切片，在我看来是横切。我想在第一条垂直切片里看到的是：一部分 schema 变更、一个新 service 被建起来、以及前端上一个最小化的呈现。我要的是竖着走，不是横着走。明白吗？好，我要去骂它一顿了。坏小子。不，我不浪费 token 光整活。

"第一条切片太横了"，我就先这么说，看它能不能领会。概念上讲得通吧？我很喜欢回到这些老书的一点是：我们这个年代真正在做的，是把最佳软件实践用英语重新说出来，而这些 20 年前的书早就说完了。把它们扔进 prompt 是一座金矿。但即便如此，AI 也不会每次都做得完美。

"完成课程可得积分并在 dashboard 可见"。对，这才是漂亮的垂直切片：体量确实不小，覆盖一堆故事，但结尾能看到可见的东西，AI 之后可以往上叠。看到为什么这比第一条好了吧。好。看着不错，我们越来越近了。在家跟着做的各位——你们不在家，但你们懂意思——希望你们也看到同样的东西、养出同样的直觉。

### 可独立认领的 issues 与并行化

好，经过几轮确认后，我们应该得到一组 issues。这些 issues 的设计目标是"可独立认领"，于是看板就长成这样：一组工单带着一堆独立关系——这个要先于那个，那个要先于这个——这意味着你可以开始并行：让多个 agent 同时开工，因为这个先做，做完之后这两个可以被独立的 agent 同时认领。

做过 agent 并行化的举手。好。这让你的计划本质上变成有向无环图（DAG）：比如三个阶段——第一阶段做这一个，第二阶段做下面两个，第三阶段做第三个再挂上去。而这还是个简单计划，你可以同时跑很多个计划。能做出非常漂亮的并行化，后面细讲。

这就是我为什么偏爱这种看板而不是顺序计划：顺序计划基本只能被一个 agent 认领。看，这份计划就只是一个循环，只有一个 agent 能做，因为阶段有编号、不可并行。明白吗？好。

issues 有了。……别再问我要……哦不，它在往 GitHub 上建，我真不想要。哦不，你这个蠢货。改成建在 issues 里。不行，不够精确。蠢货，改成"建成本地 markdown 文件，引用本地版本"。抱歉各位。到这一步，我们手上有了一堆本地 issues，可以开始循环实现。也是从这个节点起，人类离开循环。

到目前为止——我拉一张我们正在走的这条流程的总览图——我们从点子出发，对点子做了一轮 grilling（研究和原型这两步可以跳过），把它变成了 PRD、目的地文档，再把 PRD 变成了看板，这些步骤全部经过人审。然后是实现阶段：我们退后，让一个 agent——或多个 agent——去消化这块看板。这意味着：我们花了大量时间规划，但我们为 agent 排好了大量工作。可以把它想成白班和夜班：白班是人——规划一切、备好一切；踢给夜班之后，AI 就可以纯 AFK 地干活。

### 练习 4：跑起 AFK agent（Ralph 循环）

那具体长什么样？好，允许它，完美。下一个练习，也是最后一个：跑你的 AFK agent。我管它叫 Ralph，因为它本质上就是一个 Ralph 循环。这个 prompt 我想逐行讲。

它干的第一件事：我们跑 Claude，鼓励它完全 AFK 地干活。脚本一会儿看，大意是：issues 目录里的本地 issue 文件在上下文开头注入。做法在 once.sh 里——仓库里就是个 bash 脚本：把所有 markdown issue 抓进一个本地变量，于是这个 issues 变量装着整个 backlog；再抓最近五次提交（原因等下讲）；然后抓 prompt，用 `claude` 以 `--permission-mode acceptEdits` 跑起来，把这些全喂进去。implement 长这样。

这就是这个循环的极简版。当然它还不是循环，只是跑一次。循环在上面那个 AFK 版本里，复杂不少。关键是我们还会在 Docker 沙箱里跑。我不想让你们在自己笔记本上装 Docker——还得下特殊镜像，会把会场 Wi-Fi 打爆——所以我演示就好，你们不用跑。待会儿细讲。但这个"跑一次"至关重要：反复跑它，你才能看到 agent 会做什么、怎么干活，prompt 需要什么调整你才看得到。

看 prompt：本地 issue 文件已传入；"只做 AFK issues"，合理；"如果所有 AFK 任务完成，输出'没有更多任务'"；然后"挑下一个任务"。我们在干嘛？我们在运营一个 backlog，给 AFK agent 认领。前面这一切——直到这块看板——都是在给夜班排队。夜班、这个 Ralph prompt，它自己对"什么算好任务"有想法：优先做关键 bug 修复、然后是开发基础设施、然后是曳光弹、然后是抛光快赢和重构。然后是一段简单的完成任务的指令：探索仓库、用 TDD 完成任务（稍后讲），然后跑一些反馈循环。

来试试，看会怎样。好，issue 文件建好了，可以出发。我退出，clear，然后跑——在哪来着——ralph-once.sh。跟着做的朋友也可以跑。能看到它就是在 Claude 里带着 prompt 和全部 issues 跑起来。

### 深模块 vs 浅模块

最后一节我讲两件事。第一，你脑子里大概有个问题：假设我手上这个代码库很烂——特别复杂，AI 在里面从来干不出好活，其实大多数人进去也干不出好活——怎么把它变好？第二，我展示我的并行化配置。

先讲烂代码。图在哪，在这。John Ousterhout 在《软件设计的哲学》（A Philosophy of Software Design）里讲了他心目中理想的模块类型。想象一个长这样的代码库：每个方块是一个文件，文件对外导出东西供别处使用，于是出现这种奇怪的依赖：这个文件可能依赖那个，也可能依赖那个。

如果这些文件都很小、导出的东西也不多，John 会叫它们**浅模块（shallow modules）**：一大堆小碎块。这对 AI 很难导航，因为它搞不清依赖关系、找不到东西在哪，只能人工穿整张图：这个依赖这个、这个依赖这个、这个依赖这个。它也很难测试：测试边界画在哪？每个模块单独画一圈？别那么干。这个一圈、那个一圈？还是把一大组相关模块圈在一起测、然后祈祷它们能跑？

而烂测试大多就长前一种样子：AI 给每个小函数单独包一个测试边界，逐个测它们能不能跑。可比如这个模块调用那两个模块、依赖它们俩——那这个模块可能把函数用错顺序，或者它内部本来就有值得单独测的东西；你给它包测试边界时要 mock 另外两个模块吗？怎么弄？所以把代码库造得易于测试在这里是根本：代码库易于测试，反馈循环才好，AI 才能在里面干出好活。明白吗？

那好代码库长什么样？不长那样，长这样：John Ousterhout 说的**深模块（Deep modules）**——接口小而简单、肚子里功能很多。这样的模块好测：比如这两个之间有依赖，你就在这一个模块外面整个包上一大圈测试边界。你会逮到很多好东西，因为测到的功能很多；而调用方、调用这个模块的人，拿到的又是简单接口，不折腾。明白吗？深模块对浅模块。深的好，浅的坏。

我发现如果你不盯着 AI，它自己会写出一个长"浅模块"那样的代码库，所以指挥它时要非常非常小心。这也是为什么在 PRD 里——PRD 在哪？在 issues 里，gamification system 下面……当然没找到，在这——我专门有"数据模型与模块"一节：明确写这个 gamification service 是一个新的深模块，我们围绕它做测试，它的接口长这样、长那样；progress service 也要改、lesson route 要改、dashboard route 要改等等。我对要动的模块极其具体，并且在整个规划和实现过程中始终把这张模块地图放在脑子里。明白吗？非常有用。

它还有另一个用处。除了让 App 更可测，你还得到了一个心理小戏法。我续杯水，你们想想是什么。先问你们几个问题：觉得自己"有了 AI 反而比以往任何时候都累"的举手。觉得自己"对代码库的了解不如以前"的举手。对，这是真实现象：因为跑得快、委托得多，我们对代码库失去了感觉。而失去了对代码库的感觉，我们就没法改进它——等于把代码库的形状委托给了 AI。我觉得这不好。

那怎么既跑得快、脑子里又留得住足够的空间？我认为这就是办法：你思考的不仅是"在代码库里造大块头、大 service"，你更应该做的是**设计这些模块的接口，然后把实现委托出去**。换句话说，这些模块变成灰箱：你只需要知道它们的形状、知道它们干什么、大概怎么表现，而内部的实现可以委托。我发现这非常舒服：我不必评审模块里的每一行，不必知道它干的每件事，我只需要知道它在特定条件下有特定行为、会干成它的事。等于：我对代码库有大图景、懂里面每一块的形状、懂所有接口在干什么，但内部可以委托出去。这让我既保住了对代码库的感觉，又保住了理智。明白吗？

### 改善代码库架构 skill

你可能会问：怎么把一个长"浅"那样的代码库变成长"深"那样？怎么把模块加深？我们有个 skill，希望在里面……肯定在。这个 skill 就叫 improve codebase architecture，直白得很。跑起来。它会扫描代码库、看看这里有什么。做练习的可以自己跑。它在探索架构、探索在这个代码库里怎么干活，然后尝试找到可以把模块加深的地方。很简单。

它在这里找到的一个特别酷的东西：我的 course-video-manager App 里有个视频编辑器——浏览器里的视频编辑器，相当硬核，是块不错的工程。我想找一个办法，把前端到后端整条链包成一个单一的大模块，好让我测"我在前端按一下、一路通到后端"。我最后靠在这两个类型之间用一个可辨识联合（discriminated union），用这个 skill 把整个视频编辑器基础设施包成了一个巨大的、可以从外部测试的模块。这意味着 AI 能看到整条流、能在整条流上操作、能在整条流上测试。说实话，AI 改动这个编辑器的能力是翻天覆地的变化——不给好测试的话，让 AI 搞视频编辑器相当残暴。所以今天你们哪怕只带走一件事：回自己仓库跑一下这个 skill，看看会发生什么。

### Push vs Pull：编码规范

这里的问题是：在早期规划阶段，该不该使劲优化计划？很多人在这么做，这想法本身很好。回到阶段图：假设这些阶段你都走完了，跟 LLM 把一切都聊透了，你知道要去哪，做完了这份"旅程-目的地"文档。那该不该继续打磨、打磨 PRD 直到它成为你能想象的最完美 PRD？我觉得没什么价值，因为旅程文档只是"你想去哪"的提示，真正该花力气的地方是 QA——QA 大概也能 AFK 做，但我的经验是从里面榨不出多少汁。真正要紧的是在最初的 grilling 会话里跟 AI 达成对齐。

再来一个。还有吗？好。

（观众："在你的工作流里，怎么让它按你想要的方式写代码？这样到 code review 时代码至少是熟悉的、用的是你想用的库？"）

对，这问题其实前面出过：怎么把你的编码规范强加给 agent？本质上是让它按你的口味写代码。有两种方式：**push** 和 **pull**。什么意思？push 是你把指令推给 LLM：往 CLAUDE.md 里写点什么，比如"说话像海盗"，这条指令永远会发给 agent，对吧？这是 push 动作，你在把 token 推给它。pull 是你给 agent 一个"拉取更多信息"的机会，比如 skill：skill 放在仓库里，带一小段描述头，告诉 agent"你想要的时候可以来拉"。

我对 code review 和编码规范当前的思考是这样的：对实现者（implementer），编码规范应该以 pull 方式可用——它有疑问时能拉到答案；而对实现之后的自动化评审者（reviewer），你要 push：把信息推给评审者，说"这是我们的编码规范，确保这份代码符合它"。比如你有 skill，就把 skill 内容推给 reviewer，让 reviewer 手里同时有写好的代码和编码规范可以比对。希望这回答了你的问题。我还可以给你看一个自动化版本。

### Sand Castle：并行 AFK 循环

正好，趁热打铁，现在就做。我最近花了大概一周造了个东西，叫 **Sand Castle**。我对市面上跑 AFK agent 的那些方案不太满意，就写了这个：一个跑这些循环的 TypeScript 库。它有一个 run 函数：创建一个 worktree、在 Docker 容器里沙箱化，然后在里面跑一个 prompt。worktree 就是一个 git 分支，代码在里面，之后可以合并。

打开给你们看，有些查看方式非常漂亮。它让你跑这类自动化循环，还能极简单地在多个不同 agent 之间并行。进我的 sandcastle 文件，看 main.ts，我们走一遍。这跟我前面给你们看的那个 Ralph 循环类似，是把串行升级成并行的地方。

首先有一个 planner，拿着一个 plan prompt 看一遍 backlog，挑出一定数量要并行做的 issues——记得我给你们看的那个带阻塞关系的看板吧，它把所有阶段都算出来。这里说，假设我们有一组 issue——这些胶水代码你们可以无视——就是一组带标题、带工作分支的 GitHub issues。然后对每个 issue，建一个沙箱，在沙箱里跑一个 implementer，把 issue 编号、issue 标题和分支传进去。这跟我们刚才跑的循环是同一个。

然后如果产出了 commit，我们就评审这些 commit。这就是那个循环。对 commit 怎么办？交给一个 merger agent：拿着 merge prompt、拿着建出来的分支和 issues，把它们合进去；类型、测试这些合并问题，它顺手解决。

这就是我相当长一段时间以来大多数项目的工作流，好用得不得了。想深入可以去看看 Sand Castle。正面回答你的问题：reviewer 我用 push 推编码规范，implementer 我用 pull。另外我实现用 Sonnet、评审用 Opus，因为评审是我需要"聪明劲儿"的地方。

这就是整条流程：全程把代码库的形状放在心上。这不是一台 specs-to-code 编译器，不是一个闷头吐代码的 AI。我们对自己想要的模块和代码库形状是有意为之的；我们用 grilling 会话、用反复捶打点子来保证尽可能对齐；我们不过度投入 PRD——不逐字读它、甚至不太想它；然后把它变成一组可并行的 issues，交给多个 agent 并行处理；实现完，往死里 QA 和 code review，然后不断回到实现。

有一件事我没怎么提：QA 阶段的作用是给那块看板产出更多 issues。甚至实现跑着的时候，你就可以 QA 已完成的部分、回去加更多 issues。看板几乎可以无限地加阻塞 issue。全部做完——代码你满意了、工作你满意了——再拿去和团队分享、做完整评审。走到这一步，大概是一个开发者或两三个开发者管着这条流水线，怎么合并回主线就看你自己的了。

当然，这一切都由你自定义。这只是我验证过可行的东西，我不是来向你推销某套方法论的。如果这场你们只带走一样东西：回 Amazon 上把那些老书买一堆回来——读它们真的太有启发了。AI 之前年代的写作本身就很有味道，而且每一页我都发现有用、有意思的东西。
