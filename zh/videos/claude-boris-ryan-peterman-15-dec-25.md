## 逐字稿

[`0:02`](https://youtu.be/AmdLVWMdjOk?t=2) 模型迭代得太快了。3 个月或 6 个月后再问我这个问题，我的答案会完全不同。这位是 Boris Cherny，Claude Code 的创造者、前 Meta Principal Engineer。我们聊了塑造他职业生涯的一切。你能解释一下什么是潜在需求（latent demand）吗？

[`0:17`](https://youtu.be/AmdLVWMdjOk?t=17) 我认为潜在需求是产品领域最重要的单一原则。

[`0:22`](https://youtu.be/AmdLVWMdjOk?t=22) 你说过存在一些明显的文化差异，那段时间很难熬。

[`0:26`](https://youtu.be/AmdLVWMdjOk?t=26) 我的天，"难"都太轻描淡写了，那简直是噩梦。我们还聊了 Claude Code，以及 Anthropic 内部正在发生的事。尽管 Anthropic 的规模已经扩到三倍，工程师人均产出却增长了接近 70%，这都要归功于 Claude Code。不要为今天的模型做产品，要为 6 个月后的模型做产品。我推荐给所有人、对我作为工程师影响最大的一本技术书是……你怎么看与 Codex 和 OpenAI 的竞争？我想从你晋升 Meta 高级工程师那段讲起。让你晋升的项目背后有什么故事？当时你在做什么？如果我没记错，那个项目是 chats and groups，目的是把 Messenger 和 Facebook 拉得更近一点。我在 Meta 最早做的几个项目都与 Messenger 和 Facebook 有关，第一个大概是 Zuck 提的想法——把 Messenger 聊天和 Facebook 小组（Groups）打通。这一类项目有好几个，都在尝试把 Messenger 和 Facebook 拉近。动机是当时大家感觉这种公共空间式的社交产品正在消失，一切都在向聊天和更随性的实时空间迁移。我们试了好几版产品，chats and groups 是跑出来的那一版，当时大概是第三还是第四次尝试。我在 Facebook（也算 Facebook Groups 团队），需要和 Messenger 大量协作，而那个组织离我们非常远。这个点子其实是当时一位 PM Steve 提出来的，我觉得这事该做，就说"太好了，干起来"。于是我开始动手写，很快有了起色，我就申请加人，先后来了三位工程师：Shatambri、Crystal 和 Chaang，这是最早加入的三位，后来又有了数据科学和设计的支持。产品先在 Web 上跑起来，后来也上了移动端。我们证明了"在 Facebook 小组里内嵌聊天"这个产品方向是成立的。说实话它也有大量完全不行的地方——按现在的产品标准看，那是个特别糙的体验。当年大家都在 Web 上开发，各种 bug 都无所谓；如今视觉和质量标准都高多了。产品就这样长起来，我们团队特别小，人人都得什么都干。我记得当时没有用户研究员（user researcher），我就中午端着新功能去食堂，给食堂师傅演示："你能找到怎么打开一个聊天吗？"有时他们能找到，有时找不到。这就是观察式用户研究：看特定情境下的人能不能完成一个任务，不做过多的提示，不给太多线索，观察他们在哪里卡住、能理解什么。我们这样做，然后我把这套方法教给了团队，很快大家都中午去食堂"骚扰"食堂师傅，把他们当作典型用户，问"这个看得懂吗"。有意思的是，你所在的早期 Facebook 文化允许工程师做代码之外这么多的事——比如做用户研究，我记得你的故事里还做过设计、教人做设计。这算是 Facebook 文化里挺独特的一点。这一点非常重要。直到今天，在我现在所在的 Claude Code 团队，我们依然极其看重通才（generalist）。我喜欢和通才合作：一个会写代码的工程师，同时能做产品、能做设计、有产品直觉、愿意去和用户聊——我特别喜欢和这样的工程师共事。我们现在所有职能都是按这个标准招人的：产品经理会写代码，数据科学家会写代码，用户研究员也会写一点。我就是喜欢这样的通才。这其实也是我的成长路径——从 18 岁做第一家创业公司起我就什么都得干，进 Facebook 之前我一直待在小公司，什么都得干。进了大公司，你会被强制塞进某条泳道里，但那只是形式上的——工程本身是一个非常窄的技能集，你真正在做的是做产品或者做基础设施，端到端要处理的东西远不止写代码。在一家当时只有 Facebook 会奖励这种做事方式的公司，真的很酷。那个半年度（half）结束时我升了级，接下来那个半年度，团队里每一位工程师也都升了级。在那些早期产品里，有一个你多次提到的概念——潜在需求（latent demand），听起来它是很多产品方向的出发点。你能解释一下什么是潜在需求吗？

[`5:42`](https://youtu.be/AmdLVWMdjOk?t=342) 我认为潜在需求是产品领域最重要的单一原则。尤其是回头看 Facebook 的成功产品，每一个都带着潜在需求的影子。比如 Marketplace，它源于一个观察：当时 Facebook 小组里 40% 的帖子都是买卖东西。Facebook 小组本来不是为交易设计的，但人们就这么用它。这很妙——你把产品设计成"可以被 hack"的样子，允许用户稍微"滥用"它，然后你看数据，看他们是怎么滥用的，再围绕这个用法做一个正式产品。于是先有 Facebook 小组，再有买卖小组（buy/sell groups），后者显然成功了，因为人们本来就想在 Facebook 小组里买卖、做生意，接着 Marketplace 就顺理成章地出来了——它只是人们已有意图的自然延伸。Facebook Dating 也差不多，当时的观察大概是：60% 的主页浏览（profile view）来自异性、且彼此不是好友。这种传统的"互相偷看"的行为，对当时像 Nate 和 FMS 这些人来说，就是产品能成立的证据。产品上的原则是：你永远无法让人们去做他们还没在做的事。你能做的是找到他们已有的意图，然后引导它，让他们更顺手地兑现这个意图、更轻松地做成想做的事。在你的故事的这个阶段，你提到过跨组织协作——你正是弥合 Messenger 和大量小组工程工作之间缝隙的人。我很好奇，你说过存在一些明显的文化差异而且很难。对于跨非常不同文化的组织协作，你有什么建议？

[`7:30`](https://youtu.be/AmdLVWMdjOk?t=450) 我的天，说"难"实在太轻了，就是噩梦。当时的 Facebook 这边，我们只想快，只想尽快做出漂亮的产品；而 Messenger 那边满脑子都是可靠性和性能，只关心这个。完全是两个极端的价值观。而且这不只是文化差异，不只是工程师之间的事——对方团队的工程师对我们是有戒心的，因为我们会拖累他们的性能指标。组织设计上，他们的组织是为了"慢速发布且不弄坏指标"而搭建的，我们是为了"快速发布"而搭建的，目标也完全不同：他们背的是 SLA 正常运行时间，我们看的只是日活和互动。所以我的心得是：这类文化价值观扎得很深，不只是嘴上说说，你能真切地在组织设计、目标设计、每一个环节里看到它。说实话，那个项目后来失败的原因之一（它最终其实演化成了一个成功的产品，但那一版失败了）正是这种价值观差异。所以从根本上说，如果你想让价值观差异巨大的团队真正协作成功，必须找到某种共同目标、共同利益、共同信念，找到一个双方都觉得"要是成了会非常有意思"、愿意一起验证的假设。而 chats and groups 这个东西对 Facebook 来说真的很酷，但对 Messenger 来说出于种种原因并没有那么酷。以你现在所知，回到那种项目里你会怎么改变做法？

[`9:10`](https://youtu.be/AmdLVWMdjOk?t=550) 我大概会直接去找 Zuck 说：如果你真想做这件事，就应该把 Messenger 并回 Facebook 组织里。后来这种事确实发生了，而且发生了不止一次——Messenger 一会儿并进组织、一会儿又出去、又进来，大公司就是这样。但根本上讲，要让这种事成功，共同的上级不能是 Chris Cox 这个层级，得再往下压一层，这样组织结构上才能更协作。

[`9:39`](https://youtu.be/AmdLVWMdjOk?t=579) 明白了，把激励对齐，就不会有那种无休止的拉扯。

[`9:44`](https://youtu.be/AmdLVWMdjOk?t=584) 对，就是这个意思。在你职业生涯的这个阶段，你做过一批很有意思的副业项目（side project），我很好奇这类项目的"蝴蝶效应"。比如还没进 Meta 之前，你做过 Undux——一个 React 状态管理框架。我很好奇它对你的职业生涯有什么影响？

[`10:07`](https://youtu.be/AmdLVWMdjOk?t=607) 副线任务（side quest）对我来说太重要了，我招工程师时一定会看这一点。我想要有副线任务的人——很酷的周末项目、很有意思的副业，哪怕这个人只是特别痴迷于自己酿康普茶也行。你要的是对主业之外的世界保持好奇和兴趣的人，是更完整的人，我也最喜欢和这样的人共事。我自己的很多成长正是来自这些副业项目。拿 Undux 来说，它的起源其实是：React 的状态管理实在太复杂了。当时最先进的就是 Flux，还有个叫 Redux 的东西，而我怎么也理解不了 Redux。我自认为是个普通工程师，我是做产品的，不是那种了不起的系统工程师。Redux 那套概念——reducer 之类，为了改一小块状态要绕那么复杂的流程——我实在转不过来。于是我做了一个更简单的东西，能用。我当时在一家非营利组织做志愿者，他们开始用它，工程师们很喜欢。后来我进了 Facebook，发现大家用 Redux 用得很痛苦：内部有个 Redux 用户群，里面全是问题，而且大家问的正是我当年那些问题。当工程师或产品人遇到问题时，有时只是你的问题，但通常别人也有。培养出"这个问题可能别人也在经历"的蜘蛛感应（spidey sense）非常重要。这显然是个共性问题，从求助帖和我自己团队用 Redux 的费劲程度就能看出来。于是我在内部发布了 Undux。Undux 其实一般，算不上多好的产品，但至少比 Redux 好。在 Facebook 我其实不知道怎么推广，就发了个帖，有几个人开始用。我记得通知团队的 Jeff Case 是早期重度用户，我们为了排查它引发的几个很难缠的通知相关 bug 熬了好几个夜。我想要更多用户，于是写了个小脚本，把群里报 issue 的人爬下来，按团队计数，然后挨个给每个团队的 tech lead 和经理发消息，约一场只面向该团队的技术分享。几周之内我大概讲了 20 场、30 场、40 场，差不多这个量级。

[`12:45`](https://youtu.be/AmdLVWMdjOk?t=765) 我还记得骑着车在 Meta 园区里到处跑、到处讲，特别有意思，因为大家真的投入——有人愿意认真解决他们真实存在的痛点，大家兴奋得不行。某个时刻 Undux 成了 Facebook 最流行的状态管理框架，后来很快被 Recoil 和更现代的替代品取代，如今则是 Relay 这些了。这种副业项目会写进你的绩效评审吗？或者以某种方式帮到了你？我觉得是写进去了。按 Meta 的标准，它算是"锦上添花"，本身不足以把你送到下一个层级。不过那段时间我还有很多别的副线任务。有阵子我特别痴迷 TypeScript——那还在前公司的时候，我们在用，但好的学习资料很少。我就想"总得有人写，这么好的语言居然没有书，太疯了"，于是开始写书。TypeScript 的设计好得惊人，有很多当时其他语言根本没有的东西——那时虽然还没有条件类型（conditional type），但一切都是字面量类型（literal type），还有映射类型（mapped type），简直疯狂，连最硬核的 Haskell 玩家都会被这种语言特性折服。可当时没人写这些，我就一头扎进去写了一本书，差不多吞掉了我一年的时间。[笑声] 不推荐这么干。但深入钻研真的很过瘾。后来我还在旧金山办了当时世界上最大的 TypeScript 聚会（meetup），在那里见到了创造 Node.js 的 Ryan Dahl 等一众 JavaScript 名人。那段经历让我明白：这些人也都只是普通人。大家都在做有意思的东西，有的东西很酷，有的东西只是在特定时刻很酷，但归根结底都是人在做，任何人都做得到。

[`14:47`](https://youtu.be/AmdLVWMdjOk?t=887) 后来在 Meta、或者甚至在 Anthropic，你有用到 TypeScript 或那段时间积累的技术深度吗？有，说来有趣。我以前其实不在乎语言，直到大约十年前——我当时骑摩托车，出了个挺严重的事故，胳膊骨折了。

[`15:05`](https://youtu.be/AmdLVWMdjOk?t=905) 我的天。

[`15:05`](https://youtu.be/AmdLVWMdjOk?t=905) 两只都断了。

[`15:06`](https://youtu.be/AmdLVWMdjOk?t=906) 对，两边都吊着绷带。

[`15:08`](https://youtu.be/AmdLVWMdjOk?t=908) 天哪，那你怎么写代码？

[`15:10`](https://youtu.be/AmdLVWMdjOk?t=910) 这就是难受的地方。整整一个月我没办法写代码，之后手还是疼，写不了 JavaScript——那是我当时的主力语言。于是我被迫去学别的语言，理由特别朴素：它们需要的按键更少。我先学的是 CoffeeScript，因为括号少之类的。这语言现在应该都没了，现在没人用。学 Haskell 和函数式编程也是这么入门的——同样的效果，更少的按键，这就是当时的动机。后来我在一家对冲基金工作（进 Facebook 之前），有个同事 Rick 特别迷 Scala，我一直理解不了 Scala，是他把我带进门的，把我领进了函数式编程这个门派。直到今天，我推荐给所有人、对我作为工程师影响最大的一本技术书就是《Functional Programming in Scala》。你今天大概率不会再用 Scala，但它教你的那种思考编程问题的方式，和大多数人实践里或学校里学到的编码思维完全是两回事，它会彻底改变你写代码的方式。对我来说，Haskell、CoffeeScript 这几门关键语言是第一步，然后是 Scala，再然后是 TypeScript。这一路改变了我的思维方式：现在我写代码时是用类型思考的。代码里最重要的是类型签名（type signature），它比代码本身还重要。把它想对，代码自然就干净。在 Facebook 我主要写 Flow 和 Hack，后来在 Instagram 写 Python，这套思维都非常有用；在 Anthropic 我主要写 TypeScript 和 Python，所以确实直接相关。但更大的心得就是：用类型思考。

[`17:07`](https://youtu.be/AmdLVWMdjOk?t=1027) 在职业生涯的这个节点，你提到自己是"低配入职"（underleveled）——明明经验很多却以中级工程师进来，而且你说回头看不低配反而是幸运的。这背后的想法是什么？

[`53:21`](https://youtu.be/AmdLVWMdjOk?t=3201) Unshipping 的理念是：只往 App 里加功能，对一小部分用户是好事，但对大多数用不上这个功能的用户其实是坏事。想象一个只增不减的 App：功能不断累积，如果每个功能只有 10% 的人在用，那普通用户打开 App 看到的是一堆自己根本不用的东西——显得又乱又困惑，打开之后不知道该干嘛。软件的屏幕尺寸终究是有限的，那是稀缺资源，所有功能都在抢。你加一个功能，就等于抢走了另一个他本可以用的功能的机会。所以 unshipping 的理念是：每个功能必须迈过某个使用率门槛，迈不过就删。少部分用户会不爽，但对大多数用户是好事，平均下来对所有人都是好事。

[`1:21:03`](https://youtu.be/AmdLVWMdjOk?t=4863) 有意思，我在想 Claude Code 对那个著名的"创造者日程 vs 经理日程"意味着什么。你刚说的其实是：软件工程师正在变得更像经理式的工作——你管着一队 Claude Code，前进不再靠深度专注，而是在 20 件事之间切换。你不再有大块的专注编码时间了吗？没那么多大块了。不过我周末也写代码，我爱安静的时间。平时我每天早上起来第一件事就是打开 Claude Code——现在 Claude 里有 code 标签页，这周刚发布，但我们内部用了一阵子——每天早上我启动几个 agent，让它们把我今天的代码先跑起来。不可思议的地方在于：6 个月前你要是告诉我代码会这么写，我会说"你疯了吗，代码怎么能这么写"。但它就是成立了，这就是现在我写很多代码的方式。我先启动几个 agent，到电脑前看状态：代码没问题就直接合；有时候拉到本地，"传送"进去改一点。你等下还会聊到 Fiona，她跟你说过，她十年没写过代码了，但现在一周写好几次——因为哪怕经理的日程再疯，她可以用手机 App、可以用 Web、可以开个终端，让 Claude 替她写。我们真的活在这样一个转折里：我们做的事、我从小长大的那套东西，正在彻底改变，而且正在对所有人开放，太酷了。

[`1:23:00`](https://youtu.be/AmdLVWMdjOk?t=4980) 最后一个问题：以你现在知道的一切，回到刚入行的时候，你会给那时的自己什么建议？用常识就行。[笑声] [吸气] 尤其在大公司，有太多力量把你从常识旁边拉走：大量"组织惯性"——事情是这样是因为它一直是这样；大量错位的激励。当然也有好东西，但这些确实存在。所以用常识判断极其重要。我职业生涯早期在创业、也待过很多创业公司，那里也一样：用常识搞清楚市场要什么、用户要什么，然后做出来。相信你自己，培养你的常识。
