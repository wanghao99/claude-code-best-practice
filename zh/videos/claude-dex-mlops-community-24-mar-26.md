## 逐字稿

[`0:04`](https://youtu.be/YwZR6tc7qYg?t=4) 好，在我请出 Dex 之前，我得说我见到了 James。James，能站起来一下吗？James 今天早上告诉我他要——我们看不到二维码，你得举高点。他今晚要请大家吃饭，所有人都被邀请。所以如果你想去，扫一下那个二维码，去和 James 聚聚。太棒了，这就是我们想要的效果。

[`0:33`](https://youtu.be/YwZR6tc7qYg?t=33) 你真棒，我喜欢。好，我要请出 Dex 了。刚才有人说我们应该来一场胡子比赛，我觉得不会发生，但我可以说他准备了 200 页幻灯片要讲。

[`0:48`](https://youtu.be/YwZR6tc7qYg?t=48) 哇，158 页，就 158 页。我们会盯紧他的时间。好，现在开始。

[`0:57`](https://youtu.be/YwZR6tc7qYg?t=57) 来吧。大家好，我是 Dex。这个演讲标题很长，我不念了，因为我们要控制时间。我讲 coding agent 已经讲了挺久，基本从去年 8 月开始，11 月我们做过一次长演讲。我们一直在讲一套方法论，叫 research plan implement（研究-计划-实现，RPI）。在 HackerNews 上很多赞。大概有一万人去我们的开源仓库拿走了我们的 prompt，从初创公司到大型企业都在内部使用。

[`1:29`](https://youtu.be/YwZR6tc7qYg?t=89) 这一切始于这个人。有人看过这个演讲吗？好。Eigor 进去后说：好，我们用了大量 token、花了很多钱来换 AI 开发效率。但他发现这实际上导致大量返工。你多交付了 50%，但其中一半只是在清理上周的 slop（粗制滥造的代码）。他们发现的另一点——这些是去年的数字，没算 Opus 4.5，所以我会稍微上调一点——这套东西对低复杂度的绿地（全新）任务很好，对高复杂度的棕地（存量改造）任务不好。

[`2:02`](https://youtu.be/YwZR6tc7qYg?t=122) 我本可以给你们讲一场 RPI 有多棒的演讲，但那太无聊了，而且已有别的演讲，没看过的去看，会有更多背景。今天我要告诉你们的是我们在 RPI 上搞错的一切。我们以为把 AI 这事想明白了，而我够谦虚，错了就认。

[`2:22`](https://youtu.be/YwZR6tc7qYg?t=142) 我们搞错了好几件事。第一件，如果你今天刷了 Twitter 会很有共鸣：我认为不读代码是不行的。我也不认为你应该读很长的计划文件。这两件事是相关的。还有，如果你写的是用户在生产环境使用的代码、坏了会在凌晨 3 点被电话叫醒的那种——不许 slop。现在是 2026 年，不许再有 slop。

[`2:46`](https://youtu.be/YwZR6tc7qYg?t=166) 我们都在这条路上，都在摸索，一直都可能是错的。我们确实也做对了几件事：没有魔法 prompt；不要外包思考——你，工程师本人，是这个过程的重要部分；以及追求杠杆（leverage）。有大量代码正在被写出来，想办法确保它是对的，而不必全部读完、事后重掌方向。

[`3:05`](https://youtu.be/YwZR6tc7qYg?t=185) 很多人应该都听说过 research plan implement。有谁真的运行过这个 claude 命令？Research codebase？好。如果你们是这样跑的，手别放。跟我说说这系统怎么工作。有谁这样跑过吗——"嘿，我要做这个东西，去做研究"，或者去抓一个 ticket 之类的？那 create plan 这个 prompt 呢？好，几只手。

[`3:28`](https://youtu.be/YwZR6tc7qYg?t=208) 你们中有多少人是这样跑的：嘿，我们要做这个东西。是的。有谁是这样跑的："和我来回讨论，先从你的开放问题和大纲开始，再写计划"？好，你们中的一些人发现了魔法咒语。但大多数人没有。我们会讲为什么这是个问题。

[`3:44`](https://youtu.be/YwZR6tc7qYg?t=224) 从去年 10 月起，我们基本与数千名工程师合作过，从微型创业公司到财富 500 强。我们一次又一次地发现：把这些工具给一个专家，效果极好。他们每周坐下来跟 Claude 聊 70 个小时，开始疯狂交付。然后他们把工具交给自己的团队，效果就不总是那么好了。

[`4:03`](https://youtu.be/YwZR6tc7qYg?t=243) 人们拿不到好结果，所以我们扎进用户堆里去搞清楚哪里出了问题。第一个问题是：人们得不到好的研究。这个我们 11 月讲过，这是极少数我复用的幻灯片：你会圈出代码库的一个区域，说"我们要在这里构建东西"，然后启动一个 coding agent 会话，派 subagent 沿着垂直切片深挖代码库，只为了拿到压缩的上下文——关于我们即将构建的东西，什么才是真的。

[`4:32`](https://youtu.be/YwZR6tc7qYg?t=272) 我们说：保持客观、压制观点、不要放任何实现细节。你只是想压缩事实。代码今天是怎么工作的，什么是真的？一个熟练的工程师很擅长拿着 ticket 写出一些问题，引导模型去碰代码库里所有关键的部分。比如 ticket 是"新增一个跨租户 reticulate splines 的端点"，我们会说：告诉我端点是怎么工作的，追踪所有涉及 splines 的逻辑流，找到做 reticulation 的 worker。

[`5:03`](https://youtu.be/YwZR6tc7qYg?t=303) 如果这是你的 ticket，很多人会这样跑：直接说"嘿，research codebase，我要构建这个"。问题在于：好的研究全是事实。但你告诉模型你要构建什么，你就会得到观点。模型为什么不该有观点，我们后面讲。这又回到 Netflix 的 Jake 那句话：不要外包思考。

[`5:22`](https://youtu.be/YwZR6tc7qYg?t=322) 另一个没起作用的地方：人们拿到的计划不好。当时那个规划 prompt 是一个巨大的单体，有 85 条甚至更多指令，里面内置了一些步骤，比如"向用户呈现设计选项""在真正写计划之前先就结构获取反馈"。

[`5:43`](https://youtu.be/YwZR6tc7qYg?t=343) 一个好的规划会话长这样：你有 Claude 的系统工具和你的 prompt，你说嘿，create plan，它加载 skill、看你的 ticket、加载你的研究文档、派一堆 subagent 去确认代码库里为真的事实——确认研究里可能没覆盖的东西。顺便说，这全都在一个大上下文窗口里。通常我用这些栏表示独立的上下文窗口，但今天这全是同一个会话——幻灯片是横的，只能并排放。

[`6:11`](https://youtu.be/YwZR6tc7qYg?t=371) agent 会来问问题：这是问题一的选项。用户选一个，再选一个，最后它说：好，这是做事的顺序，你觉得呢？用户可以说：我们要在最前面加一个测试步骤，而且我想把阶段三和四换过来。助手给出新的阶段大纲，用户确认，然后我们才写计划文件。

[`6:33`](https://youtu.be/YwZR6tc7qYg?t=393) 这是一个与用户对齐"要构建什么"的复杂过程。但对大约 50% 的人（如果没用那句"和我来回讨论"的咒语，或者 Opus 那个小时恰好犯蠢，比例可能更高），它拿到东西就直接去把计划写出来了。于是你得到的是：好，我写完计划了，没问我任何问题，替我做了所有决定。吓人。

[`6:58`](https://youtu.be/YwZR6tc7qYg?t=418) 我们把工具发给大家，有人效果好有人不好。我们深挖：差别在哪？人们真的会这么跟我说："你得说魔法咒语。"我发现我自己在企业工程师满座的 workshop 里说："各位各位，软件在这儿，但别忘了念咒语。"坦白说，很尴尬。

[`7:16`](https://youtu.be/YwZR6tc7qYg?t=436) 但如果你说了这句——"和我来回讨论，先从你的开放问题和大纲开始，再写计划"——agent 就会来问你问题。这不是用户的错。如果你造了一个需要训练和练习好几个小时才能用好的工具，去修工具。我会讲我们怎么修的。

[`7:35`](https://youtu.be/YwZR6tc7qYg?t=455) 为什么这些步骤被跳过？今天我要给你的一个大要点是：你有一个指令预算（instruction budget）。我的联合创始人 Kyle 就坐在那边。他在 12 月（严格说 11 月）写过一篇很好的博文，引用了一篇 arXiv 论文——这也是去年的数字，现在可能更高——前沿 LLM 只能稳定遵循大约 150 到 200 条指令。超过这个数，它就是"半关注"所有指令，剩下全靠掷骰子。

[`8:04`](https://youtu.be/YwZR6tc7qYg?t=484) 所以如果你的 prompt 有 85 条指令，再加上你的 CLAUDE.md、系统提示、工具和 MCP——是的，你不太可能获得对工作流的完整遵循。我们后面讲怎么修。

[`8:16`](https://youtu.be/YwZR6tc7qYg?t=496) 另一件我认为对人们真的没起作用的事：我们当时主张去读产出的计划。这是我 11 月在台上告诉大家"必须读计划，否则不奏效"。有些人甚至会把计划提 PR、一起代码评审。但一千行的计划大概对应上下 10% 的一千行代码，而计划里可能藏着意外。

[`8:38`](https://youtu.be/YwZR6tc7qYg?t=518) 你去评审计划，然后去写代码，结果代码不一样了。你让同事"花一小时读读这个，告诉我哪里不对"，然后你去实现，实现出来不一样，他们又得去读代码，看哪里有意外、哪里变了。这不是杠杆。杠杆是用更少的工时获得更多产出。

[`9:01`](https://youtu.be/YwZR6tc7qYg?t=541) 所以新的建议是：不要读计划，请读代码。工作量差不多，去别处找杠杆。我会讲我们怎么找到更好的杠杆。

[`9:10`](https://youtu.be/YwZR6tc7qYg?t=550) 你可能会说："嘿 Dex，8 月的时候你说不用读代码，说计划就够了，直接交付让 Claude 干活就行。"我错了，我够谦虚，错了就认。这在当下其实是个很大的争论。请读代码。我们试了大概六个月不读代码，结局不好，不得不把那个系统的大部分拆掉重写。

[`9:32`](https://youtu.be/YwZR6tc7qYg?t=572) 你可能说："嘿 Dex，别人就不读代码。"Beads，30 万行还在涨，据说没人读过那些代码。OpenClaw 的 Pete 说："我知道结构和组件、它们怎么拼在一起，但我不是每行 PR 都读。"这些是开源项目，不收钱。

[`9:58`](https://youtu.be/YwZR6tc7qYg?t=598) 它们是非常酷的项目，我对维护者的成就深表敬意——但风险等级仍然不同。你把 OpenClaw 搞坏了，很多人会不高兴；但这和你身处受监管行业、交付生产 SaaS 代码是两回事。所以如果有人依赖你的代码，我求你了，请读它，请读它。我们有一个职业要守护。2026 年应该是"不再 slop"之年。

[`10:25`](https://youtu.be/YwZR6tc7qYg?t=625) 字面意义上的所有人都在讨论 slop 和 craft（手艺）的区别。这也是我对 agent swarm 和那套"_gas town_"持保留态度的原因：你仍然需要能保证质量，快 10 倍但 6 个月后全部扔掉毫无意义。

[`10:40`](https://youtu.be/YwZR6tc7qYg?t=640) 所以，目标定在 2 到 3 倍。怎么度量、怎么真正达到并保持接近人类的质量，那是另一场演讲。但我会讲目标和你要想的事：高杠杆的规划；不外包思考；读代码并拥有代码；以及理想情况下，消灭魔法咒语。

[`11:02`](https://youtu.be/YwZR6tc7qYg?t=662) 我们得到了更好的研究、更好的计划、更好的杠杆。我逐一讲：总体上我们认识到了什么，具体我们做了什么，以及你在围绕 coding agent 构建工作流和系统时可以做什么。

[`11:15`](https://youtu.be/YwZR6tc7qYg?t=675) 前面说了熟练的工程师能把 ticket 拆解成问题、问题引出研究，研究非常客观。具体做法：我们直接把 ticket 从做研究的上下文窗口里藏起来，而且是确定性地藏。一个上下文窗口生成问题，然后一个完全不知道我们要构建什么的新鲜上下文窗口去产出研究文档。

[`11:38`](https://youtu.be/YwZR6tc7qYg?t=698) 如果你熟悉查询规划（query planning）的概念，这很平凡。概念上类似，只是对象是 LLM 读代码库。

[`11:48`](https://youtu.be/YwZR6tc7qYg?t=708) 我玩 agent 挺久了，在做 coding agent 之前写过一篇《12 Factor Agents》，据说是最早大讲 context engineering 的文章之一。context engineering 有两种读法，大多数人跳进了第一种。有人在做 RAG 管道吗？做过 RAG 的举个手？好，今天有些人不太敢举手。

[`12:10`](https://youtu.be/YwZR6tc7qYg?t=730) 那种读法是"塞更多信息进去"。塞太多，模型消化不了。我其实认为更有意思的读法是：更好的指令、更简单的任务、更小的上下文窗口。

[`12:22`](https://youtu.be/YwZR6tc7qYg?t=742) 当然，现在大家都认识 Jeff 了，不用我再介绍。我们把上下文窗口的这个现象叫"笨区"（dumb zone）：20 万 token 里你大约能用 16.8 万，还有一些要留给输出，各有各的用途。平均在 40% 左右——取决于你在干什么、用户消息和文件各占多少——你会撞上结果退化的点。

[`12:48`](https://youtu.be/YwZR6tc7qYg?t=768) 显然有时用到 60% 也还能出"对你够用"的结果，但上下文窗口用得越少，结果越好。我们在 Databricks 的朋友刚讲过：你挂太多 MCP，整个上下文窗口塞满了你根本不在乎的工具使用说明，等到真写代码时，模型已经不擅长遵循你的指令了。所以你不只是给了模型太多信息，你还很可能给了它太多指令。

[`13:12`](https://youtu.be/YwZR6tc7qYg?t=792) 我们当时的做法里，有一件事很说得通：用 prompt 做控制流。这是客服的例子：是投诉就走这条，是产品反馈走那条，是账单问题走那边。

[`13:27`](https://youtu.be/YwZR6tc7qYg?t=807) 可以换成：先把输入分类，再喂给一系列更小、更聚焦的 prompt，每个的指令和可选动作少得多。我相信很多人已经用这类手段优化过管道性能。

[`13:43`](https://youtu.be/YwZR6tc7qYg?t=823) 原来是一个 85 条指令的巨型 prompt。做对了你会走完这些阶段；任何一条指令没被遵循，就会跳过那些真正带来高杠杆的东西。

[`13:54`](https://youtu.be/YwZR6tc7qYg?t=834) 我们把它拆成了多个 prompt。以前是 research、plan、implement，现在是 questions、research、design、structure、plan、work、implement、PR。今天没时间讲 implement 那半了。我们把规划拆成了设计讨论、大纲、计划。以前 85 条指令，现在全部低于 40 条，这很令人兴奋。有些还能更小，我们还在迭代。

[`14:18`](https://youtu.be/YwZR6tc7qYg?t=858) 教训是：如果能用控制流做控制流，就别用 prompt 做控制流。if 语句非常强大，LLM 非常擅长分类。这不只对 coding agent 成立，对你构建的任何基于 LLM 的系统都成立。

[`14:31`](https://youtu.be/YwZR6tc7qYg?t=871) 有意思的是，我们写了那么多文章，上台说"全脂 agent 不行，别光在循环里调工具，要做 context engineering，建工作流、图、微 agent"，告诉所有人别那么干。然后 8 月我们转过身说"这个 Claude Code 挺好的"，然后一转身写了个巨型单体 prompt。所以是时候喝下自己的酷爱了。管好你的指令预算。

[`14:56`](https://youtu.be/YwZR6tc7qYg?t=896) 怎么获得更好的杠杆？我们把东西拆开以获得更好的指令遵循，这是三个不同阶段。但我们同时拿到了更多杠杆，我讲讲为什么。因为即使计划是一千行、代码是一千行，你的设计讨论可能只有 200 行，而你在那一刻有大量重新掌舵的机会。

[`15:12`](https://youtu.be/YwZR6tc7qYg?t=912) 它长这样：我们要去哪？最终方案长什么样？有当前状态、期望的最终状态、要遵循的模式。你们多少人派过 coding agent，结果它在你的代码库里找到了做某件事的错误方式、跟着坏模式走？是吧。

[`15:29`](https://youtu.be/YwZR6tc7qYg?t=929) 这就是你的机会：把它认为相关的所有模式读一遍，然后说"不，我们不是这样做原子 SQL 更新的。那是某个已经离职的工程师写的，很疯，所有人都讨厌。去那边找我们的正确做法。"

[`15:40`](https://youtu.be/YwZR6tc7qYg?t=940) 它会记录已敲定的设计决策，会问开放问题。这相当于把 Claude Code 的 plan mode 加上 ask user question 工具，全部倾倒进一份你可以交互、可塑且灵活的文档。

[`15:54`](https://youtu.be/YwZR6tc7qYg?t=954) Matt Pocock 有个概念叫 design concept（设计概念）：锁在上下文窗口里的那个东西——你和 agent 之间关于"构建什么、怎么构建"的共享理解。我们把它放进一份 200 行的 markdown 产物里。

[`16:07`](https://youtu.be/YwZR6tc7qYg?t=967) 于是我们有了人机对齐（human-agent alignment）。思路是：强迫 agent 把它找到的一切、想做的一切、以为你想要的一切全部倾倒出来，就它不知道的东西向你提问。这样你可以在进入下游之前给 agent 做"脑部手术"。

[`16:24`](https://youtu.be/YwZR6tc7qYg?t=984) 一切都关乎"不要外包思考"。你要给 agent 每一个机会，让它在你去写两千行代码之前展示它哪里想错了。

[`16:35`](https://youtu.be/YwZR6tc7qYg?t=995) 200 行代替一千行，杠杆多了一点。大纲也给了我们更好的杠杆。如果说设计是"我们去哪"，结构大纲就是"我们怎么去"。或者对一个天天开会开到崩溃的工程师来说：一个是架构评审，一个是 sprint 规划会——我们要做什么，以及怎么拆成任务。

[`16:56`](https://youtu.be/YwZR6tc7qYg?t=1016) 我们把设计和 ticket、研究放进一个新的上下文窗口，生成结构大纲：阶段的高层概览——不是要写的具体代码，而是大概长什么样、按什么顺序做改动、一路上怎么测试。

[`17:12`](https://youtu.be/YwZR6tc7qYg?t=1032) 我并不是每个阶段之间都真的测试，但如果敏感、难或复杂，我要能在它写完所有代码之前抓住问题。我要确保每个两三百行、四百行的块是对的。

[`17:23`](https://youtu.be/YwZR6tc7qYg?t=1043) 这些文档意味着更轻的评审。同一个功能的两份文档对比：计划 8 页，结构大纲 2 页左右，短得多。

[`17:33`](https://youtu.be/YwZR6tc7qYg?t=1053) 我喜欢这样类比：有人写过 C 头文件（.h）吗？有。好，如果计划是实现，大纲就是 C 头文件——只有签名和要改的新类型，刚好够你看到 agent 在想什么、错了就纠正。

[`17:50`](https://youtu.be/YwZR6tc7qYg?t=1070) 这样做的原因是：尽管试遍了每一个模型、怎么 prompt、怎么 eval，我们都无法让模型停止写"横向计划"——这是治它们这个毛病的最好办法。所谓横向计划是指：模型爱写"先把所有数据库做完，再把所有服务做完，再把所有 API 做完，再把前端做完"，等你回过神已经站在 1200 行代码的另一头，跑不起来，现在你得去找哪块坏了，因为一路上没有任何东西可以测试。

[`18:24`](https://youtu.be/YwZR6tc7qYg?t=1104) 无论模型自检还是人类跳进去检查对错。我们在各种规模的组织里都看到非常有效的做法，我称之为"纵向计划"（vertical plans）。这就是我在 AI 之前构建的方式：先做一个 mock API 端点，让前端先跑通，接上线，再 mock 服务层，再做数据库迁移，最后把所有东西拼起来。

[`18:46`](https://youtu.be/YwZR6tc7qYg?t=1126) 代码总量一样，但你有这些检查点，能看到是否跑通；不通就停下来修，再继续做剩下的。这些也只是 markdown 文档。你可以也应该要求更多细节。它们从高层开始，但举个例子："我觉得你这块做不对。告诉我你在想什么。"它就把类型和签名倒出来了。

[`19:04`](https://youtu.be/YwZR6tc7qYg?t=1144) 然后从计划本身获得更好的杠杆。和以前一样，我们拿着那个产物，连同之前的所有产物构建上下文，然后写计划。如果你用过 create plan，就是完全一样的模板、一样的设置、一样的 prompt——但它是给 agent 的战术文档。对齐已经做够了，我只会抽查它，深度评审留给真正的代码。

[`19:28`](https://youtu.be/YwZR6tc7qYg?t=1168) 如果你用过 RPI 的计划，它们长这样：模型说"嘿，这是我要做的所有改动"。

[`19:35`](https://youtu.be/YwZR6tc7qYg?t=1175) 这个杠杆最重要的部分不止关于你和 agent。人机对齐很重要，知道 agent 要干什么并纠正它很好，但如果你和一个工程师团队协作，我们发现把这些设计讨论、结构大纲拿去评审很有价值——我说了别评审计划，但这些更短的文档非常非常好用。

[`19:57`](https://youtu.be/YwZR6tc7qYg?t=1197) 在 HumanLayer，我们大部分代码的 owner 不是我，是我联合创始人，而我故意把我的设计讨论发给他。我们没有强制步骤，但我想确保等走到代码评审时，那就是一句"对，这就是我要的"。这样我的坏决定在一份 200 行的文档里就被拦下来了，而不是等我写完代码、跑通了、产生感情了之后。这非常非常强大。

[`20:22`](https://youtu.be/YwZR6tc7qYg?t=1222) AI 之前，换一种方式理解是省时间。你会说："这是个两天的功能，我要做这么多事，编码大概 2 到 4 小时。"如果你只是拿起 Claude Code 让它替你交付，确实有提速，因为编码从几小时变成 20 分钟。但它仍然是两天的功能，因为我仍然要和团队对齐要做什么，仍然要代码评审、改东西，可能还要跨我不拥有的仓库协作，最后我们仍然要验证和测试。

[`20:47`](https://youtu.be/YwZR6tc7qYg?t=1247) 但如果你用 AI 辅助规划和对齐，那边的时间也省下来了，而且对齐质量高得多。代码评审和返工也短得多，因为大家都知道要来什么，评审的团队早已有机会把你扳回正道。优秀的团队一直这么做——他们有个会叫架构评审，决定技术设计文档：我们到底怎么构建这个东西。

[`21:12`](https://youtu.be/YwZR6tc7qYg?t=1272) 至于测试与验证——抱歉，我没有好答案，那是另一整场演讲。如果你去了楼下 Drew 的演讲，结束后去找 Drew Brun，他会把测试与验证讲个明白。

[`21:21`](https://youtu.be/YwZR6tc7qYg?t=1281) 我们把这一切拼起来：五个研究与规划阶段。流程是 questions、research、design、structure outline、plan、worktree、implement，最后是 pull request。这些首字母拼不出好缩写，所以我们挑了喜欢的几个，叫它 CRISPY。从 RPI 到 CRISPY。就是这样。
