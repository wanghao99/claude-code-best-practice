## 逐字稿

[`0:01`](https://youtu.be/PQU9o_5rHC4?t=1) 在 Anthropic，我们的思考方式是：不为今天的模型做产品，而是为六个月后的模型做产品。这至今仍然是我给做 LLM 产品的创业者的建议：去想模型今天还做不好的那个边界在哪里，因为它终将变好。Claude Code 的全部代码都被反反复复写了又写。六个月前存在的 Claude Code 代码，现在一处都没有了。你去尝试一个东西，交给用户，和用户交流，学习，最终也许会得到一个好想法，有时候不会。你是不是心里也在想，也许六个月后就不用提示得那么细了？模型自己就能搞定？

[`0:36`](https://youtu.be/PQU9o_5rHC4?t=36) 也许一个月后吧，

[`0:38`](https://youtu.be/PQU9o_5rHC4?t=38) 一个月后就不再需要 plan mode 了。欢迎来到本期 Light Cone，今天我们请到一位非常特别的嘉宾，Claude Code 的创造者、工程师 Boris Cherny。Boris，感谢你来做客。

[`0:59`](https://youtu.be/PQU9o_5rHC4?t=59) 谢谢你们邀请我。

[`1:00`](https://youtu.be/PQU9o_5rHC4?t=60) 也谢谢你造出了让我连续三周睡不好觉的东西。

[`1:07`](https://youtu.be/PQU9o_5rHC4?t=67) 我已经对 Claude Code 非常上瘾，感觉像装了火箭助推器。到这个时候，大家是不是已经这样好几个月了？我记得大概是 11 月底，我的很多朋友都在说：有什么东西变了。

[`1:21`](https://youtu.be/PQU9o_5rHC4?t=81) 我记得我自己第一次有这种感觉，是在我刚做出 Claude Code 的时候，那会儿我还不知道自己是不是摸到了什么了不得的东西。我隐约觉得是，然后就睡不着了。

[`1:28`](https://youtu.be/PQU9o_5rHC4?t=88) 是的。

[`1:29`](https://youtu.be/PQU9o_5rHC4?t=89) 就那样连续三个月。

[`1:33`](https://youtu.be/PQU9o_5rHC4?t=93) 那是 2024 年 9 月。对，就是连续三个月，我一天假都没休，周末连轴转，每天晚上都在干活。我当时就想："天哪，我觉得这事要成了。还不知道它有没有用，因为那时候它还不会写代码。"

[`1:48`](https://youtu.be/PQU9o_5rHC4?t=108) 回头看从那时到现在，眼下最让你意外的是什么？

[`1:54`](https://youtu.be/PQU9o_5rHC4?t=114) 难以置信我们还在用终端。终端本来应该只是起点，我没想到它会成为终点。第二个意外是它居然真的有用，因为一开始它并不怎么会写代码。甚至到 2 月我们 GA 的时候，它大概也只写了 10% 左右的代码。我并不是真用它写代码，它写得不好，大部分代码我还是手写。所以我们的押注真的兑现了——它变擅长了我们当初押注它会变擅长的事，而这在当时并不明显。在 Anthropic，我们的思考方式是：不为今天的模型做产品，而是为六个月后的模型做产品。这至今仍然是我给做 LLM 产品的创业者的建议：去想模型今天还做不好的那个边界在哪里，因为它终将变好，你只需要等。

[`2:39`](https://youtu.be/PQU9o_5rHC4?t=159) 往回追溯，你还记得最初是怎么想到这个点子的吗？能给我们讲讲吗？是灵光一闪，还是你脑子里最初的版本是什么样的？

[`2:47`](https://youtu.be/PQU9o_5rHC4?t=167) 说来好笑，这事非常偶然，就这么一步步演化成了现在的样子。在 Anthropic，我认为长期以来押注的都是 coding，押注的是通往安全 AGI 的路径就在 coding。

[`3:03`](https://youtu.be/PQU9o_5rHC4?t=183) 这一直是思路，实现路径是：先教模型写代码，再教它用工具，然后教它用计算机。你能从这一点看出端倪——我在 Anthropic 加入的第一个团队叫 Anthropic Labs，它产出过三个产品：Claude Code、MCP 和桌面应用。所以你能看到这些东西是怎么交织在一起的。至于我们做的这个产品，压根没有人让我去做 CLI。我们大概知道是时候做某种 coding 产品了，因为模型看起来已经就绪，但还没有人真正做出把这种能力利用起来的产品。所以即便到今天，仍然有一种疯狂的产品过剩感（product overhang）。而当时更夸张，因为还没有人做过这个。于是我开始瞎折腾，我想："好，我们做个 coding 产品，第一步干什么？我得先搞懂怎么用 API，因为那之前我没用过 Anthropic 的 API。"所以我就做了一个小小的终端应用来用 API，就这么点事。它是个小聊天应用，因为想想当时的 AI 应用——对今天不会写代码的人来说，大多数人用的也就是个聊天应用。所以我做的就是聊天应用，跑在终端里，我可以提问，它给回答。后来 tool use（工具使用）发布了，我就想试试，因为我不太明白这是什么东西。我心想，这东西挺酷，但真有用吗？可能没用。试试再说。

[`4:25`](https://youtu.be/PQU9o_5rHC4?t=265) 你把它做在终端里，只是因为这是最容易让东西跑起来的方式。

[`4:29`](https://youtu.be/PQU9o_5rHC4?t=269) 对，因为不用做 UI。

[`4:30`](https://youtu.be/PQU9o_5rHC4?t=270) 明白。

[`4:31`](https://youtu.be/PQU9o_5rHC4?t=271) 那时只有我一个人

[`4:32`](https://youtu.be/PQU9o_5rHC4?t=272) 在开发。那正是 IDE、Cursor、Windsurf 起飞的时候。你有没有压力，或者收到很多建议，说我们应该把它做成插件，或者干脆做成一个功能齐全的 IDE？完全没有压力，因为我们连要做什么都还不知道。团队当时完全处于探索模式，我们隐约知道想做 coding 方向的事，但不清楚具体做什么，没有人有足够高的把握。弄清楚这个就是我的工作。于是我给了模型 bash 工具，这是我给它的第一个工具，就因为我觉得那好像就是我们文档里的示例。我直接拿来用，是 Python 写的，我把它移植成 TypeScript，因为我就用这个写。那时候我不知道模型能用 bash 干什么，就让它读个文件，它 cat 了一下文件，我说酷。然后我想："你到底能干什么？"我问它"我在听什么音乐？"它写了一段 AppleScript 去操控我的 Mac，到我的音乐播放器里查我正在放的歌。

[`5:24`](https://youtu.be/PQU9o_5rHC4?t=324) 天哪。

[`5:26`](https://youtu.be/PQU9o_5rHC4?t=326) 那还是 Sonnet 3.5。

[`5:28`](https://youtu.be/PQU9o_5rHC4?t=328) 我当时根本没想到模型能做到这个。那大概是我人生中第一次"感受到 AGI"的时刻，

[`5:34`](https://youtu.be/PQU9o_5rHC4?t=334) 我当时就是："天哪，这模型就是想用工具，它满脑子只有这个。"

[`5:39`](https://youtu.be/PQU9o_5rHC4?t=339) 这挺迷人的。Claude Code 以这么优雅、简单的形态做得这么好，其实有点反直觉。终端存在很久很久了，而它似乎成了一个很好的设计约束，带来了很多有趣的开发者体验——比如感觉不像在工作，作为开发者就是觉得好玩，我不用去想文件都在哪。而这一切几乎纯属偶然。

[`6:09`](https://youtu.be/PQU9o_5rHC4?t=369) 对，是偶然。我记得终端版在内部开始流行之后——说实话，做完这东西之后，大概第一个原型的两天后，我就把它发给了团队内部试用（dogfooding），因为你知道，如果你有个点子又觉得有用，第一件事就是发给别人，看他们怎么用。第二天我到公司，坐我对面的工程师 Robert，电脑上已经装了 Claude Code，正在用它写代码。我说你在干嘛？这东西还没准备好，只是个原型。但没错，在那个形态下它已经很有用了。我还记得我们做外部发布的 launch review 时——那是 2024 年 11 月还是 12 月的样子——Dario 问："内部的使用量图，那个 DAU 曲线都垂直往上了。你们是不是在强制工程师用？为什么要下这种命令？"

[`7:00`](https://youtu.be/PQU9o_5rHC4?t=420) 我说："不不，没有。我只是发了条帖子，他们自己口口相传的。"说实话，纯属偶然。我们从 CLI 起步是因为它成本最低，然后就这么保持了一段时间。

[`7:13`](https://youtu.be/PQU9o_5rHC4?t=433) 那在 2024 年那段时间，工程师们是怎么用它的？已经用它交付代码了吗，还是别的用法？

[`7:19`](https://youtu.be/PQU9o_5rHC4?t=439) 那时候模型还不太会写代码。我个人用它自动化 git 操作——到今天我可能已经把 git 忘得差不多了，因为 Claude Code 替我干了太久。还有自动化 bash 命令，这是非常早期的用例，再比如操作 Kubernetes 之类。也有人用它写代码，所以已有一些早期苗头。我记得第一个用例其实是写单元测试，因为风险更低，虽然模型当时写得还很烂，

[`7:46`](https://youtu.be/PQU9o_5rHC4?t=466) 但大家在摸索，慢慢搞清楚这东西该怎么用。

[`7:51`](https://youtu.be/PQU9o_5rHC4?t=471) 我们注意到一件事：大家开始给自己写 markdown 文件，然后让模型去读那个文件。CLAUDE.md 就是从这来的。对我来说，产品上最重要的单一原则大概是潜在需求（latent demand）。最初那个 CLI 之后，这个产品的每一寸都是靠潜在需求长出来的，CLAUDE.md 就是一个例子。还有一条也许有意思的通用原则：你可以为模型做产品，也可以在模型周围搭脚手架（scaffolding）来稍微提升性能，视领域不同也许能提升 10%、20% 这个量级，然后到下一个模型出来，这些收益基本就被抹平。所以要么你搭脚手架、拿到一点性能提升、然后再重做一遍；要么就等下一个模型，等于免费拿到。CLAUDE.md 这类脚手架就是个例子。而我觉得这正是我们留在 CLI 里的原因：我们觉得做任何 UI，六个月后都可能不再有意义，因为模型进步太快。

[`8:50`](https://youtu.be/PQU9o_5rHC4?t=530) 刚才我们还说应该对比一下 CLAUDE.md，你说了一句很深的话：你的 CLAUDE.md 其实非常短，这几乎和大家预想的正相反。为什么？你的 CLAUDE.md 里都有什么？

[`9:03`](https://youtu.be/PQU9o_5rHC4?t=543) 好，来之前我特意看了一眼，我的 CLAUDE.md 里有两条，就两行。第一行是：每当我提 PR，启用 automerge，这样一旦有人批准就直接合并。这样我只管写代码，不用在 code review 之类的事情上来回折腾。第二行是：每当我提 PR，把它贴到我们内部团队的 stamps 频道，好让人 stamp 一下、给我解除阻塞。而其他所有指令都在我们签入代码库的那个 CLAUDE.md 里，整个团队每周都会多次共同维护。经常有人 PR 里犯了完全可以避免的错，我就直接在 PR 上 @ Claude，就说"把这条加进 CLAUDE.md"，我一周要做好多次这种事。

[`9:52`](https://youtu.be/PQU9o_5rHC4?t=592) 你们需要压缩 CLAUDE.md 吗？我肯定到过那个阶段，顶部提示说你的 CLAUDE.md 已经几千 token 了。你们碰到这种情况怎么办？

[`10:03`](https://youtu.be/PQU9o_5rHC4?t=603) 我们的 CLAUDE.md 其实很短，大概也就几千 token 的样子。如果你碰到这个问题，我的建议是：删掉你的 CLAUDE.md，从零开始。

[`10:11`](https://youtu.be/PQU9o_5rHC4?t=611) 有意思。

[`10:12`](https://youtu.be/PQU9o_5rHC4?t=612) 很多人会把这个过度设计，而模型能力是每个版本都在变的。所以你要做的是用最小代价让模型回到正轨。删掉 CLAUDE.md 之后，如果发现模型跑偏、做错了事，再一点一点往回加。你很可能会发现：每一代模型，你要加的东西越来越少。说实话，我自认为是个相当普通的工程师，不用什么花哨工具。我不用 Vim，我用 VS Code，因为它更简单。我也不是很——

[`10:44`](https://youtu.be/PQU9o_5rHC4?t=644) 等等，真的吗？我一直以为你在终端里做这个东西，肯定是个铁杆终端党，只用 Vim、觉得 VS Code 那帮人不行的那种。

[`10:53`](https://youtu.be/PQU9o_5rHC4?t=653) 我们团队里确实有这样的人，比如 Adam Wolf，他就在我们团队，他的态度是"想让我放弃 Vim，除非从我冰冷的尸体上踏过去"。所以团队里绝对有很多这样的人。这也是我很早就学到的一点：每个工程师握开发工具的姿势都不一样，喜欢用的工具也不一样，不存在一个对所有人都有效的工具。但我觉得这也是 Claude Code 能做得这么好的原因之一，因为我的思路是：做一个我自己会用、对我自己说得通的产品。用 Claude Code，你不需要懂 Vim，不需要懂 tmux，不需要会 SSH，这些都不用会，你只要打开这个工具，它就会引导你，这些事它都替你干。

[`11:30`](https://youtu.be/PQU9o_5rHC4?t=690) 你们怎么决定终端的输出要多详细？有时候得按 Ctrl+O 展开看。团队内部会不会为长短吵得不可开交？毕竟每个用户都有意见，这种决策你们怎么做？

[`11:47`](https://youtu.be/PQU9o_5rHC4?t=707) 那你的意见呢？现在是不是太啰嗦了？

[`11:50`](https://youtu.be/PQU9o_5rHC4?t=710) 不，我爱死这个详细输出了。因为有时候它真会跑飞，我在旁边看着，能飞快读出来"不不不，不是这样的"，然后按 Esc 停掉，就像眼看着一大片 bug 农场正在成形时把它整个掐掉。当然，那通常是我没把 plan mode 用对的时候。

[`12:07`](https://youtu.be/PQU9o_5rHC4?t=727) 这种东西我们可能改得很频繁。我记得早期——大概是六个月前——我试着在内部去掉 bash 输出、只留摘要，因为我想这些又长又大的 bash 命令输出我根本不关心。结果给 Anthropic 员工用了一天，所有人都造反了：我要看到我的 bash 输出。因为它确实很有用，比如 git 输出也许没什么用，但如果你在跑 Kubernetes 任务之类的，你确实想看到。我们最近把文件读取和文件搜索折叠了，你会注意到，以前显示"读取了 foo.md"，现在显示"读取了 1 个文件""搜索了 1 个模式"。这个改动我认为六个月前是发不出来的，因为模型还没准备好，它还是会经常读错东西，作为用户你得守在旁边，抓错误、调试。但如今我注意到它几乎每次都在正轨上。因为它用工具用得太多，改成摘要反而好得多。我们上线后自己内部吃了一个月狗粮，然后 GitHub 上的用户不喜欢。有个很大的 issue，大家说不行，我要看细节，这反馈特别棒。于是我们加了一个新的 verbose 模式，在 /config 里可以打开 verbose mode，想看所有文件输出的可以继续看。然后我又去那个 issue 里回帖，大家还是不满意——这也很棒，因为我最喜欢的事就是听用户的反馈，听他们到底想怎么用。于是我们继续一轮一轮迭代，把它打磨好，做成大家想要的样子。我现在很惊讶自己有多喜欢修 bug。你只需要有非常好的日志，然后哪怕只说一句"嘿，去看看这个对象，它以这种方式出错了"，它就会去搜日志，把一切查清楚。你可以建一条生产隧道，它会替你看生产数据库。这太疯狂了。修 bug 很快就会变成"从 Sentry 复制 markdown"，再过不久就直接走 MCP 了。就像自动修 bug、自动写测试——他们管那个新词叫什么来着，创业工厂？对。

[`14:10`](https://youtu.be/PQU9o_5rHC4?t=850) 对。现在有各种新理念，比如不用人审代码。我是老派，所以喜欢详细输出，喜欢说"哦，你在做这个，但我要你做那个"。但现在有一派完全不同的思路：只要有一个真人需要看代码，那就是坏事。

[`14:30`](https://youtu.be/PQU9o_5rHC4?t=870) 是的，是的，是的。

[`14:31`](https://youtu.be/PQU9o_5rHC4?t=871) 这很耐人寻味。
