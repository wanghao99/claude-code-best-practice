[`2:42`](https://youtu.be/IDSAMqip6ms?t=162) 我们可以说是稀里糊涂走到这一步的。我加入 Anthropic 的时候，我们当时还在不同团队。那时 Claude Code 有个前身，叫 Clyde，拼起来大概是 CL C cliop 那样。它是个研究项目，启动要一分钟，是个很重的 Python 程序，要先跑一堆索引之类的东西。我刚加入时想提交我的第一个 PR，就像新手一样纯手写 [笑声]——我完全不知道有这些工具，不懂这些门道。我把 PR 挂上去，Adam Wolf——他做过我们团队一段时间的经理，是我入职带教伙伴——直接把 PR 拒了，说：这是你手写的？你在干嘛 [笑声]？用 Claude。他当时自己也在大量折腾 Claude。于是我试了试 Claude，把任务描述给它，它一次就把这东西做出来了。

[`3:39`](https://youtu.be/IDSAMqip6ms?t=219) 那还是 Sonnet 3.5 的时代，所以哪怕是这种很基础的任务，我还是得修一两处，而且那个 harness 非常老，跑一次要五分钟，等得要命。但它确实能跑通，我当时就震惊了：这居然是可能的。这也让我脑子里的齿轮转了起来：也许你其实根本不需要 IDE。

[`4:02`](https://youtu.be/IDSAMqip6ms?t=242) 后来我用 Anthropic API 做原型，最省事的方式就是在终端里写个小应用，这样就不用做 UI 什么的。我开始写一个小聊天应用，然后就开始想：也许可以做个类似 Clyde 的东西。于是就做了个“迷你 Clyde”，结果没花多少工夫，它就比预想有用得多。对我来说最大的顿悟时刻，是我们开始给模型工具的时候。它立刻就开始用工具了，那个瞬间太疯狂了。模型天生就想用工具。我们给了它 bash，它就开始用 bash、写 AppleScript 来自动化各种东西，用来回答问题。我说这是我这辈子见过最离谱的事，之前从没见过。因为那时我只用过 IDE 里的文本编辑，单行补全、多行补全之类的东西。所以 Claude Code 就是从这儿来的：一边做原型，一边用一种很粗糙的方式看到了可能性的边界，两股线汇到了一起。

[`5:03`](https://youtu.be/IDSAMqip6ms?t=303) 这东西最后出奇地有用，我想我们这边也是一样。对我来说，魔法时刻大概是 Sonnet 4、Opus 4 的时候，我当时就想：“天哪，这东西真的能用。”

[`5:17`](https://youtu.be/IDSAMqip6ms?t=317) 有意思。给我讲讲那个工具时刻吧，因为这是 Claude Code 特别的一点：它直接写 bash，而且写得非常好。以前的很多 agent 架构，甚至今天任何做 agent 的人，第一反应可能都是：好，我们给它一个查找文件的工具，再给它一个打开文件的工具，为 agent 可能要做的各种动作写一堆自定义封装。但 Claude Code 就是用 bash，而且用得特别好。你们从中学到了什么？现在这个阶段，Claude Code 其实已经有一批工具了，大概十来个吧。我们几乎每周都在增删工具，所以这事儿变化很频繁。但今天确实有一个搜索工具，专门用来搜索。这么做有两个原因：一是 UX，这样可以把结果展示得更友好，因为现在大多数任务仍然有人类在环里；二是权限。比如你在 Claude Code 的 settings.json 里说这个文件不许读，我们就得强制执行。对 bash 我们也能强制，但如果有专门的搜索工具，执行起来会更高效一点。不过总体上我们确实想少铺工具，尽量让模型保持简单。比如上周还是两周前，我们下线了 ls 工具，过去我们离不开它，但后来我们做出了一套办法，能在 bash 层面强制执行这套权限系统。也就是说在 bash 里，如果我们知道你不许读某个目录，那 Claude 就不能 ls 那个目录。既然能一致地强制执行，这个工具就不需要了。这很好，Claude 少一个选择，上下文里也少一点东西。

[`7:06`](https://youtu.be/IDSAMqip6ms?t=426) 这么说吧，Boris 定技术方向，我们推出的很多功能背后都是他的产品远见。我把自己定位成更像支持角色：一是确保我们的定价和打包方式能让用户共鸣；二是确保所有功能顺利走完整个发布流程——从决定哪些原型一定要内测，到给内测定质量阈值，再到把这一切传达给最终用户。另外我们确实也在做些新东西。可以说历史上 Claude Code 大多是自下而上长出来的：Boris 和很多核心成员自己冒出了这些好点子，比如 to-do list、subagent、hook，这些都是自下而上来的。而当我们考虑扩展到更多服务、把 Claude Code 带到更多地方时，很多就要更“自上而下”一点：好，去和客户聊，把工程师拉进这些对话，给这些服务排优先级，然后逐个拿下。

[`12:14`](https://youtu.be/IDSAMqip6ms?t=734) 是，这有意思。这类决策还有几个。比如不做代码编辑器、就在终端里，所以它能访问你的文件；它跑在你自己电脑上，而不是云端的虚拟机里。这样你就可以反复地用：不断积累你的 CLAUDE.md 文件，不断搭建 slash command 等等，从一个非常简单的起点出发，变得非常可组合、可扩展 [嗤笑]。我好奇你们怎么想这个问题：如果有人想做 agent——大概不会做 Claude Code，而是做别的东西——你怎么得到那个简单的小包，然后随时间推移不断扩展、越来越强？

[`15:51`](https://youtu.be/IDSAMqip6ms?t=951) 明白了。有个我想深入聊聊的话题：怎么做出一个好计划？就是刚才说的 feature dev 那套。因为我们和 Every 的同事都在摸索一些小技巧，我很好奇我们还漏掉了什么。举个例子，计划制定过程中有个反直觉的步骤：哪怕我还不太确定要做的到底是什么，脑子里只有一句话——“我想要 X 功能”——我也会让 Claude 直接实现，什么都不给它。然后我看它做了什么，这能帮我看清“我实际想表达的是什么”，因为它犯了各种错，或者做了我没预料到的事，这些可能恰恰是重点。然后我把这次一次性的开发整个丢掉，把从中学到的东西拿来给真正的功能开发写一份更好的计划规格。这在以前是绝不会做的：还没写清楚 spec 就放一个工程师去做，成本太高了。但现在让 Claude 在你的代码库里跑一遍、干点活，你能从中学到东西，反过来指导你真正要做的计划。
